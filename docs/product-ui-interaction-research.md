# 页面交互调研与优化方案

调研日期：2026-10-02。对象：当前 PySide6 桌面工程。方法：读取实际控件/回调代码、8 个真实 Qt 控件离屏截图与尺寸记录、主流程与既有测试证据核对、公开交互规范参考。没有进行用户访谈，也未读取实时桌面页面；以下不称为真实用户满意度或 Windows 实机验收。

## 1. 产品判断

目前优先解决“怎么进入、下一步点什么、正文放在哪里、成果怎样找回”。主要能力已经存在，服务正确和用户容易完成是两种验收，界面需单独验证。

建议默认采用**写作优先布局**：章节树 + 正文，预览按需展开，工具面板默认收起；有任务时显示结果/进度，有问题时显示对应清单。研发工作区采用另一上下文，集中处理成员、关系、矩阵、影响和集合，不把这些视图同时挤到编辑器旁。

本轮读取时既有 CORE/V3.0～V3.3 勾选为 39/40、31/32、25/27、31/32、25/26，共 151/157；这是任务快照，不是全 UI 可用性结论。保留这些进度，新交互差额归独立 [UI 优化任务](../openspec/changes/product-ui-interaction-polish/tasks.md)。

2026-10-02已完成第二次计划复核，最终实施范围、来源语义和依赖以[最终计划](product-ui-interaction-final-plan.md)及同change规格为准；[执行台账](product-ui-interaction-execution.md)提供可直接复制的持续执行指令。本研究的截图/几何仍保留为原调研证据。

## 4. 页面结构与关键交互

### 首页：继续工作和开始文档

首屏给最近文档的“继续编辑”，以及“导入文档”“新建文档”“打开已有文档”。有最近记录时继续编辑优先，无记录时导入优先。“更多工具”收纳互转和 PDF，保持原快捷入口可搜索。

主区域接 DOCX/Markdown 导入；单份自动识别，多份按用户明确选定的建项语义处理，不能默认把多份 Word 拼成一份项目。已有项目导入保留当前缓冲，新项目在新窗口/结果中打开；接收外部修订是明确独立动作。转换卡区域保留直接转换，拖放高亮和提示随目标区域一致。

### 导入：默认路径只做必要决定

选源后显示名称、位置、预计章节数和可读性摘要，主操作“开始导入”。“调整章节与设置”打开已有细调页，正文前言/范围/规范等按原契约处理。预检和实际导入共享决策，不能仅为了隐藏页而忽略结构决定。

处理中阶段提示可取消，成功从首页直接进入编辑；结果以一行“已导入，2处待完善”留在成果面板。缺图、公式/文本框给“定位/原件”，不要求先处理才进入编辑。严重输入无结果时保留选择及设置、给换文件/重试。

### 编辑：正文优先、其他按需

顶部一行文档名/版本/真实保存状态，主操作导出 Word，副操作检查/更多。路径和来源指纹移入展开详情。左树保留章节搜索；当前章大纲改可收起，常见低分辨率默认收起。正文默认获得主要空间，预览可侧栏或切页，选择不修改内容和保存状态。

工具栏分两层：常用格式组带溢出；文件状态与保存等保持明确可见。底部搜索/问题/改动仅在主动打开或有需查看的结果时展开，用户手动打开的面板不得被后台更新擅自关闭。允许“恢复默认写作布局”，不清理章节内容/会话。

### 出稿：一次发起、成果持续可查

点击顶部导出 Word默认整份/当前内容/有效目录；按钮旁显示“含2章未保存修改”等事实。更多设置提供多格式、范围、来源与版式，严格模式显式选取。

成果面板按本轮实际格式列出路径/状态：可用即能打开，PDF失败不撤回Word/HTML。原轮补缺与最新新轮分成不同动作，记录各自来源；最新内容生成后旧成果仍保留。等待和重试走原 TaskRunner；用户能继续编辑，迟到事件不能覆盖新的文档/轮次。

### 批量交付：从选文档开始

入口先给新建或打开已有批次。新建表单列项目、变体、格式、位置，可移除失效成员；调用现有队列计划服务生成同一 batch 格式。结果每成员/格式独立状态与动作，先显示可用项，未完成可继续补；高级详情保留清单/JSON，不能要求人工编辑JSON才起步。

### 模块、辅助及研发上下文

模块空状态给从当前章节创建/安装，所选模块可预览后插入引用或复制；固定版本及升级差异沿用 V3.0。辅助面板首先说明本地资料范围，资料和建议用切页，选中后共用来源/差异详情与采纳/撤销，模型未启用不占主操作。

研发成员、矩阵、影响和版本集合沿 RD 计划作为可选工作区页。本次研究只定义其页面一致性，具体关系/复核功能仍由 RD 完成，不再造另一任务清单。

## 5. 状态、焦点与兜底共用规则

| 情况 | 页面反馈 | 用户继续路径 |
|---|---|---|
| 正常运行 | 文件/章节和阶段，不显示假 ETA | 可继续编辑，开始按钮防重复 |
| 可读稿已生成/Word待刷新 | 对应成果立即可开，剩余阶段标待处理 | 打开可读稿/之后补刷新 |
| 一格式失败 | 只该行失败，其他行可用 | 重试此格式，不要求重新选文件 |
| 原内容后来改了 | 旧轮记录实际来源 | 补旧轮或生成最新新轮，含义明确 |
| 目录无效 | 就地说明实际回退位置 | 打开目录/更换位置，输入保留 |
| 面板关闭/清空缓存 | 内容和成果保留 | 从成果/历史或视图命令找回 |
| 源条目/选区过期 | 待应用内容保留，显示重新定位 | 不覆盖新内容，继续其他编辑 |

焦点不被普通成功提示抢走；有输入的面板关闭后回触发控件/原编辑器。Esc优先关闭当前临时层，再按已有任务取消语义处理，不一次关闭多个层。所有关键动作有文字和键盘入口，颜色不是唯一状态含义。坏输入/不可选动作说明原因与下一步，不通过空白禁用按钮让用户猜。

## 6. 可验证的改进目标

| 编号 | 验收情景 | 目标 |
|---|---|---|
| I-1 | 首页拖入/按钮选同一 DOCX、MD | 同一真实建项服务，源已选后≤2次主要提交；输入选择不重复 |
| I-2 | 打开有效项目，未主动打开底部/右侧面板，1280×720 | 常用按钮文字可读；单栏正文目标≥560×320，不能靠扩大实际窗口冒充通过 |
| I-3 | 1024×640及长文档名 | 保存/导出/更多可见；其他动作通过溢出访问，路径省略可复制 |
| I-4 | 一次 Word/PDF/HTML 部分失败 | 每文件状态与打开/补缺明确；成果面板非模态，编辑焦点不被普通完成夺走 |
| I-5 | 原轮重试、新轮生成、等待中改章 | 来源区分且旧轮不改源；后台执行，过期结果不覆盖新轮 |
| I-6 | 未准备 batch.json/模块库为空 | 能用表单建立首个批次，能创建/安装首个模块，实际服务生成结果 |
| I-7 | Ctrl+F/Ctrl+Shift+F/Ctrl+B/Ctrl+I、Tab/Esc | 真实焦点下范围/动作一致；输入法组合不中断；缺实机证据单列 |
| I-8 | 125%/150%、深浅主题、取消、无 Word | 每环境单列，保留可用成果及设置；离屏尺寸不能当真DPI验收 |

尺寸目标是布局验收，不要求在用户主动展开所有侧栏时仍保持同一正文宽度；可切单栏/隐藏面板。首次用户试点建议 3～5 位角色分别走导入、改章、出稿、补缺，记录实际成功点/误点/步骤与弹窗；这是待做试点，不是本轮已调研用户数据。

## 7. 实施分批与边界

独立 change `product-ui-interaction-polish`，5批/20项，默认 UI-A→B→C→D→E。第一批目标是默认写作/出稿闭环；随后高级能力入口和验收。不修改当前 CORE/V3/RD/V3.4 等任务进度，不重建解析器、导出器、关系或队列。

| 批次 | 重点 | 复用 |
|---|---|---|
| UI-A | 首页拖放/命名、顶部主操作、导入主次路径、命令归组 | intake_entries、注册表、quick export |
| UI-B | 工具栏溢出、Dock默认布局、窄窗口与快捷键 | 编辑器、Qt布局/动作、会话 |
| UI-C | 成果持久视图、逐格式动作、后台补缺/新轮、轻提示 | TaskDock、TaskRunner、ExportReport、交付结果 |
| UI-D | 批次表单、模块库下一步、辅助切页、可行动空状态 | V3.0/3.2/3.3 已有服务；RD用同一交互原则 |
| UI-E | 真实入口/焦点/缩放与窗口验收、资料更新 | 现有相关GUI测试 + 本轮研究样例 |

推荐在当前正在执行批次结束后优先补 UI-A/B/C，再接 RD 和表格计划。已开始的实施继续；UI-D可依实际高级界面使用频率安排。此前241项是旧规划范围，新包另加20项，不把全部旧未勾选任务视为本包责任。

最终包内默认A→B→C→D→E，验证随批进行。有效旧会话优先恢复；成果扩展既有TaskDock而非另造状态系统。5.3真实实机试点缺环境保持未勾选，继续5.4及无依赖任务；Screen reader及用户访谈仅后续观察。补旧轮/新current-buffer/换目录重新导出行为已在最终设计与规格明确。

## 8. 调研依据

- 常用操作先呈现、低频高级选项按需展开，参考 [NN/g：Progressive Disclosure](https://www.nngroup.com/articles/progressive-disclosure/)。在本项目中的具体分组来自代码和场景判断。
- 模态会阻断当前窗口；局部输入错误适合就地显示，按钮文字应说明具体动作，参考 [Microsoft：Dialog controls](https://learn.microsoft.com/en-us/windows/apps/develop/ui/controls/dialogs-and-flyouts/dialogs)。这里只借鉴交互原则，不要求将 Qt 改成 WinUI。
- 键盘顺序应保留操作含义，参考 [W3C：Focus Order](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html)；本文将其作为桌面键盘设计参考，不声称完成 WCAG 合规认证。

本轮只产生调研、交互方案与实施计划；截图是当前真实控件的合成内容样例。对话中的可点击方案是拟议交互，使用模拟数据，不是真实导入或出稿。
