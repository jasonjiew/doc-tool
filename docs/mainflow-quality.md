# 主流程质量检查与团队共享配置

适用：现有编辑、源检查、CLI、构建前检查及设置页。没有新增工作流引擎、依赖或审批平台；旧项目 schema 1/2 均可继续使用。

## 1. 主流程与兼容边界

1. AI/用户在已确认范围内编辑 Markdown。
2. 设置页和实际检查器读取同一份规则；规则、术语优先使用项目 `quality/`。
3. 运行源检查，查看内容发现及规则实际执行状态；检查按钮不会保存术语或迁移配置。
4. 配置有效时按现有构建管线生成、刷新并校验产物。配置失效或规则执行异常时停止本次出稿，保留既有产物，不用默认回退冒充检查成功。
5. 普通内容提醒与既有发布策略不被全局升级；质量门禁使用 `check` 的严重度/阈值与明确的严格检查。技术出稿完成不等于内容获批或正式业务验收。

新增 `module_sections`、`table_schema` 默认关闭；不要为应用新工具全库整改、重导入或升级项目模式。先选择一个模块验证规则与误报情况，再由团队确认启用范围和严重度。

## 2. 配置实际来源

| 优先级 | 规则 | 术语 |
| --- | --- | --- |
| 项目共享（可进 Git） | `quality/rules.json` | `quality/terms.json` |
| 旧位置（兼容读取） | `.state/quality_rules.json` | `.state/terms.json` |
| 都不存在 | 内置默认规则 | 空术语清单 |

- 已有共享文件优先，损坏时明确报告配置错误，不偷偷改用本机旧文件掩盖问题。
- 加载/检查不迁移、不写回；显式保存规则或术语才写共享位置，旧文件不删除。只读项目拒绝保存。
- 仅修改规则或术语时不改 `project.yml`。保存前验证参数，非法输入不写任何文件；I/O 失败准确返回已写入项目，不声称整体成功。
- 显式空 `rules` 列表仍表示关闭全部规则。报告列出未执行事实，不能解释为规范全部通过。
- 设置页显示实际生效的规则及来源；可解析的错误配置保留原条目供修正，不静默删除未知项。
- 兼容既有规范包的 `ruleId` 和旧配置的 `rule_id`；两者冲突时报错。资源设置按原输入字段风格保存，不丢扩展元数据。
- 术语检查使用规范化词串视图；设置/规范包保留原始字符串或 `canonical` 对象及 aliases/备注。两种视图来自同一次共享读取，保存时保留原资源结构。

## 3. 模块级章节规则

复用现有 Markdown 词法解析，忽略代码围栏和注释中的示例。选择器相对 `contentRoot`，不读取选择器之外的文件。

下面是一个**新增规则对象片段**，应追加到现有 `rules` 列表，不是用它替换整份默认规则：

```json
{
  "rule_id": "module_sections",
  "enabled": true,
  "severity": "error",
  "params": {
    "paths": ["modules/*.md"],
    "exclude_paths": ["**/_index.md", "**/_revision_record.md"],
    "mode": "file",
    "section_level": 4,
    "sections": ["功能描述", "流程图", "时序图", "数据流图", "方法设计", "核心逻辑"],
    "ordered": true,
    "allow_extra": false
  }
}
```

- `file`：每个匹配文件是一个模块，适合直接从四级标题开始的拆分文档。
- `heading`：同一文件中有多个模块时配置 `module_level`（如 3）与 `section_level`（如 4），分别检查边界内的章节，不能借用下个模块的章节。
- 检查缺少、重复、顺序及规范外同级章节，定位到源文件/行。章节存在不证明内容或图示语义正确。
- 不自动猜测所有三级标题都是业务模块，也不把跨文件拆散的内容默认为已完整聚合验证。
- 没有匹配文件时报告 `not-applicable` 及原因，不宣称规则已执行；发布前应核对实际范围。

## 4. 需求明细表型规则

同样作为规则对象追加到现有列表，按真实合法表型定义，不强行让功能概览表、模块头和所有表格使用同一组列。

```json
{
  "rule_id": "table_schema",
  "enabled": true,
  "severity": "error",
  "params": {
    "paths": ["modules/*.md"],
    "schemas": [{
      "name": "功能明细",
      "match_headers": ["需求标识", "描述", "验收标准"],
      "required_headers": ["需求标识", "描述", "验收标准"],
      "required_cells": ["需求标识", "描述", "验收标准"],
      "aliases": {"需求标识": ["需求编号"], "描述": ["需求描述"]},
      "min_rows": 1
    }],
    "require_table": true
  }
}
```

- `schemas` 可配置多个合法变体，使用匹配最明确的表型；无法唯一选择时报告未完成字段检查，不猜测。
- 校验必需列、列/别名冲突、数据行数量及逐行必填单元格，复用构建端的管道转义/分隔行解析。
- 非目标表不套用规则；没有匹配的目标表时按 `require_table` 报告。
- 空白单元格属于机械检查，验收标准是否可测试、需求是否正确仍由 AI/人工判断；不自动补造需求或设计。

## 5. 配置与执行事实

- JSON 损坏/重复键、未知启用规则、错误类型、重复规则、无效正则与参数值必须可见，不能静默降级为“零发现”。
- 已关闭规则不运行；关闭项的语义参数不执行，也不会被擅自恢复成启用。未知关闭项保留并说明未执行。
- `.load()` 仍返回兼容列表，代码不能仅凭它判断配置有效；使用 `.load_result()` 查看来源和诊断。
- `ContentLinter.check_all()` 保留列表接口；`check_report()` 同时返回配置来源与各规则状态。缓存键包含配置来源、原始摘要及诊断，修复/损坏配置不会复用旧通过结果。
- `check --output json` 的新增 `quality` 字段和 CLI `lint` 数据给出 `configuration`、`rules`、启用/执行/关闭数量、`complete` 与 `cacheHit`；原有机器字段保留。
- `executed` 只表示规则函数执行完成，**不等于没有发现或业务批准**。`disabled`、`invalid`、`unknown`、`not-applicable`、`failed` 都有原因。
- 没有实际执行规则时，源检查阶段不标成功；普通检查给出限制，显式严格检查返回非通过。
- 构建失败也必须使统一检查失败，不能只因内容问题列表为空返回通过。
- GUI 当前章/所选章过滤不能隐藏项目级配置错误；“运行检查”只读术语，只有明确新增/移除操作才保存，共享词条元数据保留。

## 6. 最小接入验收

先在合成项目或获准副本中验证：合法模块、缺少章节、合法表型、空必填项、坏正则、未知规则、关闭项及零匹配选择器；对照共享与旧位置同时存在时的实际来源。

再确认源检查不写项目、坏配置停止出稿并保留上次文件、CLI 标准输出可解析、GUI 范围过滤不丢失配置错误。真实需求/详设项目的配置应用、Word 实机/版式验收及新便携包发布应按对应授权与实际环境另行完成，不能用测试源码存在或原版 EXE 代替新版验收。
