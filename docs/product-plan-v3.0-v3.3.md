编制日期：2026-10-01。目标用户继续为企业研发文档团队。本计划承接 [V2.6～V2.9](product-plan-v2.6-v2.9.md)，遵循 [流程与兜底原则](product-flow-fallback-policy.md)。本轮只创建后续规划，不改动前四版正在执行的任务、代码和进度。

## 1. 当前基础与后续方向

读取时 HEAD 为 bbfc71a，工作树 APP_VERSION 为 2.8.0，已有大量未提交实现。OpenSpec 记录为 V2.6 56/59、V2.7 39/41、V2.8 34/44、V2.9 32/39；这是读取时的任务勾选快照，不代表四版已发布或所有功能经过独立复核。旧台账部分总览滞后，执行时以 tasks 与近期实际证据重新核对。

四版都按“优先给出可用结果”设计：缺项可占位，坏可选配置回退，冲突项跳过，失败项可继续；结果集中展示自动处理/待完善/未执行。严格交付是明确选择，不成为日常编辑、协作或出稿前置。

2026-10-01 增补：[主功能优化计划](product-core-workflow-plan.md) 将导入、当前编辑内容预览、Word/PDF/HTML/源码导出与再次修订放到更高优先级。独立 change `product-core-import-export` 共 8 批/40 项，先完成主要链路，再进入下面四版；不重排正在执行的 V2 任务或四版原编号。其进度见 [CORE 台账](product-core-workflow-execution.md)。

易用性按 [默认交互契约](product-core-usability-contract.md) U-1～9执行：先交付默认单份导入/快速Word/直接打开，随后补高级范围/格式和批量/排版。已可用直接接口可供V3复用，CORE阶段交付不等于其全部40项完成。

## 3. V3.0：正文模块与产品变体

典型场景：需求、设计、测试共用术语和接口约定；A/B 两个产品型号有不同功能章节、产品名和接口参数。

| 优先级 | 功能 | 用户行为与结果 |
|---|---|---|
| P0 | 正文模块库 | 从章节提取正文及资源，搜索/预览，可带参数，保存独立版本 |
| P0 | 固定引用与复制编辑 | 引用使用项目内固定副本；复制编辑成为普通正文，不被库升级改动 |
| P0 | 同源展开与定位 | 预览/Word/HTML/检查共用内容，图片/题注正常，定位原模块 |
| P0 | 选择升级与追踪实例 | 看差异后选引用升级，实例身份稳定，明确纳入才计需求覆盖率 |
| P1 | 产品变体 | 选择章节范围、变量/模块覆盖，独立目录出稿并展示实际范围 |
| P1 | 展开兼容副本 | 给旧应用或外部作者一份普通 Markdown 项目，保留资源/来源说明 |

设计边界：本地声明式模块，不做在线知识平台/脚本表达式；固定副本避免共享盘变化影响出稿。变体只支持显式章节列表和文本覆盖，不做复杂产品配置语言。模块库与 V2.6 片段库、V2.8 规范包分别处理正文复用、插入文本和底模规范，代码层共享索引/资源工具。

默认兜底：缺模块优先同版本缓存，其次占位；参数缺失用声明默认/字面值；循环停止该引用展开，其余正文继续。严格策略独立验证。使用新标记的项目需要新应用，旧版本兼容通过展开副本实现。

文档：[提案](../openspec/changes/product-v30-content-reuse/proposal.md)、[设计/验收](../openspec/changes/product-v30-content-reuse/design.md)、[任务](../openspec/changes/product-v30-content-reuse/tasks.md)。

## 4. V3.1：团队查证、分工和交接

典型场景：作者先查某章由哪次提交改动，文档负责人给现有意见分配处理人；没有共同 Git 环境时交换章节包。

| 优先级 | 功能 | 用户行为与结果 |
|---|---|---|
| P0 | 章节历史 | 查看可获取的 Git/重命名记录，与当前缓冲比较；无 Git 自动本地历史 |
| P1 | 负责人/我的待办 | 在原意见/影响对象上分配和筛选，不重复维护另一套“是否通过” |
| P0 | 内容交接包 | 打包所选正文/基准/资源/模块，接收方看差异后选择应用 |
| P0 | 部分应用/幂等 | 一章冲突不阻止其他章，同包重导不重复，异项目可新副本导入 |
| P1 | 渐进命令注册 | 本版菜单/面板同动作、同状态，有最近使用，保留旧命令适配 |

设计边界：负责人是协作字段，不要求账号/登录；复用已有评审生命周期和 Git 操作。交接是导出本地文件，不自动发送或推送。Git 历史只读，旧内容采用当前新保存恢复。命令注册只迁移触及的动作，不先做全 main_window 重构。

默认兜底：无 Git 用本地记录；坏 team 配置归未分配；未知交接基准明确说明；冲突/脏内容跳过，已选合法项继续；资源冲突按内容 hash 分辨，不拿同名图直接替代。

文档：[提案](../openspec/changes/product-v31-team-workflow/proposal.md)、[设计/验收](../openspec/changes/product-v31-team-workflow/design.md)、[任务](../openspec/changes/product-v31-team-workflow/tasks.md)。

## 5. V3.2：批量交付与换机正式化

典型场景：负责人一次生成多个项目/变体的 Word/HTML，办公机没有 Word 时先拿可读包，再由有 Word 的机器补刷新。

| 优先级 | 功能 | 用户行为与结果 |
|---|---|---|
| P0 | 持久批次队列 | 提交后逐项执行，退出重启可看结果并一键继续，先串行 |
| P0 | 重试未完成项 | 只补失败/待刷新部分，重复点击不重复登记，取消保留已完成 |
| P0 | 自足快照包 | 包含 DOCX/必要源/底模/模块/资源/报告，原机器路径不是依赖 |
| P0 | 换机补刷新 | 正式化包内原快照，源后来修改不让历史包失效，Word 失败保持可读 |
| P1 | 结果索引与选择归档 | 看成员/变体/格式/状态/路径，选可用结果打包，部分范围明确 |
| P1 | 批次 CLI 与示例 | 单一 JSON 报告，可用 Windows 无 Word runner 示例，平台按实测声明 |

设计边界：复用已有 pipeline、TaskRunner、集合和 OutputState；新增编排，不重造 Word 引擎。Word 在本应用串行，忙时待刷新。首版不安装常驻服务，不要求 CI/服务器；手工和本地队列都可完整使用。PDF 调用现有转换能力，不新增排版引擎。

默认兜底：单成员/单格式失败保留其它成果；无 Word 保留待刷新 DOCX；登记失败保留安全新副本。源后来改变仅提示捕获版本，正式化不覆盖当前项目修订表。幂等范围为本地共同登记记录，不能承诺无共同存储的跨机器全局唯一。

文档：[提案](../openspec/changes/product-v32-batch-delivery/proposal.md)、[设计/验收](../openspec/changes/product-v32-batch-delivery/design.md)、[任务](../openspec/changes/product-v32-batch-delivery/tasks.md)。

## 6. V3.3：本地写作辅助与可选模型

典型场景：写设计前查已有接口说明，发现规范缺项和术语差异；修改完成后生成修订候选，并选择可采纳部分。

| 优先级 | 功能 | 用户行为与结果 |
|---|---|---|
| P0 | 本地资料搜索 | 明确资料范围，返回出处/版本/定位；当前缓冲和陈旧来源有标记 |
| P0 | 确定性建议 | 复用规范/术语/引用/评审/影响事实，给填写提示和摘要候选 |
| P0 | 差异采纳与撤销 | 查看 before/after，选择后进缓冲，一次撤销，现有保存路径不变 |
| P1 | 可选摘要/术语增强 | 本地模型或自定义 HTTP，主动点击才调用，范围/截断可见 |
| P0 | 无模型完整使用 | 无账户、断网、超时、坏响应都有本地候选，不阻止编辑出稿 |

设计边界：先文本/术语搜索，不以向量数据库或 embedding 为前置。模型只做修订摘要和术语措辞，不自动生成整份文档、认定测试通过、建立关系或更新发布状态。采用确定性建议也不替代人工评审。

默认兜底：坏索引直接查可读文本；过期建议刷新，冲突跳过；模型不可用使用本地结果。开启模型后单次主动操作即可请求，不增加多轮确认；日常保存/检查/生成从不自动调用。真实模型连通是可选试点，不是基础版验收前置。

文档：[提案](../openspec/changes/product-v33-authoring-assistance/proposal.md)、[设计/验收](../openspec/changes/product-v33-authoring-assistance/design.md)、[任务](../openspec/changes/product-v33-authoring-assistance/tasks.md)。

## 9. 验证、取舍和旧提案归属

新增功能按用户场景/常见兜底/相关写入保护/取消验证，不为规划 Markdown 写镜像业务测试。每批直接套件通过后推进；版内实现完成再跑 `python scripts/tests/run_tests.py`。新测试文件在实施时注册，不把规划示例名称当当前已有套件。

OpenSpec 校验示例：`openspec validate product-v30-content-reuse --strict`。新增 reuse/variant/delivery/provider 功能及 CLI 都是计划接口，完成实施并核对 help 后才写成可运行示例。

| 旧候选或既有能力 | 本次归属 | 实施处理 |
|---|---|---|
| phase3 Include/共享章节 | V3.0 | 改为项目固定模块/实例来源，避免任意外部实时引用 |
| 同文档多产品型号 | V3.0 | 声明式变体，独立有效范围和产物 |
| phase3 章节 Git 历史/命令注册 | V3.1 | 本地历史兜底、渐进迁移，不改 Git 历史 |
| V2.8 评审 HTML/意见回流 | 已有基础，V3.1 复用 | 增加内容交接，不再重做意见生命周期 |
| phase3 staged/promote | V3.2 | 固定自足包处理原快照，源改变不作全局阻断 |
| V2.9 租约/集合/完整与部分恢复 | 已有基础，V3.2 复用 | 队列/包只增加编排，不重复造锁和集合服务 |
| phase3 AI provider/修订摘要/术语提示 | V3.3 | 本地路径先完成，可选两个模型用途，用户级配置 |
| 提交门禁/集中审批/身份权限 | 暂不作为新增主线 | 已有检查可提示，普通提交/编辑不增加审批 |
