# V4.2 42-A 分阶段量测（2026-10-03）

命令：`python analysis\v42\measure_staged.py`（退出码 0）
原始数据：`analysis\v42\measure-staged.json`
环境：Python 3.13.13 / Windows-11-10.0.22631-SP0 / AMD64

每档 5 次采样，冷=不用派生缓存，热=复用派生缓存；同一次运行内逐阶段计时
（discover / read / index / rules / collect），并记录峰值与对象释放。

| 章数 | 冷 p95 (ms) | 热 p95 (ms) | p95 改善 | 冷/热问题数 | 结果逐项一致 |
|---|---|---|---|---|---|
| 50 | 131.69 | 40.43 | **+69.3%** | 相等 | 是 |
| 300 | 215.79 | 211.37 | +2.05% | 相等 | 是 |
| 1000 | 649.25 | 705.77 | **−8.7%** | 相等 | 是 |

目标对照：要求主要热路径 p95 改善 ≥ 30% → **未达成**（仅 50 章档达标；
300/1000 章档接近持平甚至变慢）。50 章档未恶化，满足“不恶化超过 10%”。

真实结论（不删样本、不放宽断言）：

1. 索引复用确实减少解析工作（问题清单冷/热逐项一致），但**热路径总耗时在大档
   没有优势**，说明瓶颈不在“重复解析正文”，而在索引构建之外的部分——本轮
   `hotRead` 阶段仍对每个文件做了 `read_text` + 内容摘要，这部分随章数线性增长；
   `rules`/`collect` 阶段同样随章数增长且未被缓存。
2. 因此 42-B/42-C 的优化方向应由本次实测决定：优先减少**热路径下的读取/摘要**
   与规则遍历重复工作，而不是继续增加解析缓存。
3. 1000 章档热路径慢于冷路径，属于需要单列排查的实测异常（可能来自缓存读写
   I/O 与内存压力），未做结论性归因。
