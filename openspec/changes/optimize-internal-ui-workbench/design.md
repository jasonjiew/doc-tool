## Context

当前 Windows 桌面应用已基于 `tkinter/ttk` 建立单窗口界面，并通过应用服务层完成项目加载、校验、诊断构建、正式合并、最近项目、窗口状态持久化和目录打开等操作。长任务已经使用后台任务桥接和结构化事件提供阶段、进度、心跳、告警、错误与结果，取消仅在安全阶段边界生效。

现有能力完整，但主窗口仍以项目摘要、任务进度和持续展开的事件日志为主。新建/打开项目及构建、校验等高频操作主要依赖菜单；任务完成后缺少持续可见的后续操作；错误信息也较偏技术诊断。使用者是内部团队成员，优化重点是降低寻找入口和判断状态的成本，而不是建设面向外部用户的产品化导航体系。

本变更必须保持现有项目格式、文档处理管线、Word 自动化、安全取消、原子发布和日志脱敏语义，不增加运行时依赖，并兼容源码运行与 PyInstaller 冻结运行。

## Goals / Non-Goals

**Goals:**

- 将主窗口内容区组织为“未打开项目空状态”和“已打开项目工作台”两种明确状态。
- 把正式合并、诊断构建、项目校验及内容、输出、报告入口提升到首屏，同时复用现有命令处理函数。
- 集中呈现项目可写性、正式合并就绪状态以及操作不可用的原因。
- 继续消费现有结构化任务事件，以阶段、进度、耗时和安全取消状态呈现长任务。
- 在主窗口保留最近一次任务结果，成功时给出产物后续操作，失败时分层展示原因、建议和技术详情。
- 将事件日志降级为默认紧凑、可折叠的辅助区域，同时保留待读、复制和打开日志目录能力。
- 建立有限、统一的字体、间距、按钮层级和语义状态样式，并覆盖关键状态矩阵测试。

**Non-Goals:**

- 不迁移到 PySide、Electron、WebView 或其他 UI 框架。
- 不引入多页面侧边栏、路由体系、深色主题、复杂动画或面向外部客户的品牌视觉重构。
- 不改变 `project.yml`、项目目录、最近项目数据或窗口状态的持久化格式。
- 不修改导入、校验、构建、Word 刷新、原子发布、项目锁和安全取消的业务语义。
- 不以 UI 层重新实现应用服务，也不新增一套与现有任务事件并行的进度协议。
- 不在本变更中调整新建项目向导的步骤和业务规则；仅在需要时对齐公共样式。

## Decisions

### 1. 保留单窗口架构，在内容区按项目状态切换视图

`MainWindow` 继续作为窗口和命令编排入口。内容区根据当前是否存在已加载项目，在空状态容器与工作台容器之间切换；菜单、状态栏和窗口生命周期保持稳定。切换时更新已有控件或显示对应容器，不创建第二个主窗口。

这样能够以最小结构变化形成清晰入口，并继续复用当前菜单状态矩阵、窗口几何信息和关闭保护逻辑。

**Alternatives considered:**

- 完整侧边导航：会增加页面管理和状态同步成本，对内部单流程工具收益有限。
- 多个顶层窗口：会增加任务状态、项目状态和关闭行为的一致性风险。
- 始终显示所有区域并仅禁用控件：无法解决未打开项目时首屏信息噪声和入口不明确的问题。

### 2. 使用轻量展示状态模型统一控件状态，不复制业务判断

在 UI 层由当前项目、兼容/只读状态、Word 可用性、任务运行状态、输出与报告路径等既有信息派生一个轻量展示状态。它至少描述：当前视图、项目摘要、各高频动作是否启用、不可用原因、任务展示和结果展示。

展示状态只负责把已有事实映射为文本和控件状态。业务可执行性仍由现有应用服务和命令处理函数最终校验，避免 UI 判断成为安全边界。菜单项和首屏按钮应调用同一命令，并从同一状态刷新入口更新可用性。

**Alternatives considered:**

- 每个按钮独立判断：容易使菜单与快捷按钮出现状态漂移。
- 把全部业务状态重构为新的全局状态管理框架：超出 tkinter 内部工具的实际需要，并会扩大回归范围。

### 3. 高频快捷入口委托给现有命令

工作台首屏提供正式合并、诊断构建、项目校验，以及打开内容、输出、报告等入口。按钮只委托给现有菜单命令或抽取后的共享命令方法，不直接调用底层文档内核。菜单和键盘快捷键继续保留，作为兼容入口和低频功能承载区。

对于不可用动作，控件保持禁用，并在就绪摘要或相邻说明中显示稳定、可理解的原因；不依赖禁用按钮本身承载提示。

**Alternatives considered:**

- 从菜单移除重复入口：会破坏既有使用习惯和快捷键可发现性。
- 在按钮回调中重复服务调用：会产生两套确认、错误处理和任务启动逻辑。

### 4. 任务区继续消费现有结构化事件

任务区沿用 `task_bridge.py` 与应用管线提供的 `stage/progress/warning/error/result` 事件。阶段名称、确定性进度、心跳、已用时间和取消状态由现有事件与计时逻辑派生；UI 不估算虚假百分比，也不改变安全取消边界。

任务开始时清理或归档上一任务的瞬时进度，但最近一次终态结果保留在结果区域。取消请求后，界面明确显示“等待安全阶段结束”一类状态，并在不可取消的临界区禁用取消入口。

**Alternatives considered:**

- 新建 UI 专用进度协议：会与管线事件重复并增加不一致风险。
- 仅显示旋转式忙碌状态：无法满足大型 Word 操作的可观察性要求。

### 5. 最近任务结果作为主窗口持久区域

结果区域具有空闲、运行中、成功、失败和取消等展示状态。成功状态展示结果摘要，并仅对实际存在且适用于本次任务的产物、所在目录和校验报告提供操作。失败状态首先展示用户可理解的原因和建议操作，稳定错误码、异常摘要、日志位置等技术信息置于可展开详情中。

结果状态只在下一任务开始、项目切换或用户明确清除时更新，不使用短暂弹窗作为唯一反馈。必要的确认和阻断弹窗仍可保留，但弹窗关闭后主窗口仍可查看终态。

**Alternatives considered:**

- 只使用消息框：用户关闭后无法继续查看路径和处理建议。
- 将全部错误堆栈默认展开：会压缩主要工作区并增加非技术使用者的理解负担。

### 6. 日志采用紧凑摘要加按需展开

事件日志默认显示紧凑标题行，包含当前日志状态、待读数量和展开/折叠入口。展开后复用现有文本日志视图，并保留复制与打开日志目录能力。折叠时仍接收事件并更新待读计数；用户展开并查看后按现有语义清除或更新待读状态。

日志折叠状态在当前窗口生命周期内保持一致；除非现有窗口状态机制可以无格式变更地容纳该值，否则本变更不要求新增持久化字段。

**Alternatives considered:**

- 永久隐藏日志：会降低内部故障排查效率。
- 保持日志默认占据大面积：与高频操作和结果反馈的首屏优先级冲突。

### 7. 样式集中在现有 ttk 样式模块

在 `doc_tool/ui/styles.py` 中集中定义有限的字体层级、间距常量、主要/次要按钮样式，以及成功、警告、失败和中性状态样式。优先使用 `ttk.Style` 和系统主题能力；仅在 `tk.Text` 等 ttk 无法覆盖的控件上设置必要颜色。

语义不能只靠颜色传达，状态文本和控件标签必须同时表达含义。样式需在 Windows 高 DPI、源码模式和冻结模式下保持可读，不引入图片化按钮或新字体依赖。

**Alternatives considered:**

- 在每个控件创建处散落颜色和边距：难以保持一致且不利于测试和后续维护。
- 自绘控件或第三方主题库：增加依赖、打包体积和平台兼容风险。

### 8. 优先在 MainWindow 内分区，达到复杂度阈值后再拆组件

首轮实现可在 `main_window.py` 中用清晰的构建、渲染和状态刷新方法组织空状态、操作区、任务区、结果区和日志区。若单一区域需要独立状态或测试替身，再拆为不含业务逻辑的轻量 Frame 组件。

这避免为了视觉调整过早创建大量文件，同时通过方法边界控制 `MainWindow` 的增长。

## Risks / Trade-offs

- [主窗口继续增长，状态刷新路径变复杂] → 将控件创建、展示状态派生、状态应用和命令执行分离；所有项目、任务和结果变化统一触发刷新，并用状态矩阵测试覆盖。
- [菜单与首屏按钮可用性不一致] → 两类入口共享命令和状态来源，测试同一场景下的菜单与按钮状态。
- [禁用控件无法直接解释原因] → 在项目就绪摘要和动作区显示原因文本，不依赖工具提示或颜色。
- [日志折叠后重要错误不易被发现] → 失败结果在结果区独立呈现；日志标题保留待读/错误提示，严重事件可自动强化标题但不强制展开。
- [语义色在系统主题或高对比度环境中表现不同] → 颜色仅作辅助，始终配合文字、图标字符或边框层级；优先使用系统可读前景色。
- [结果操作指向不存在或过期文件] → 每次渲染和点击前检查路径存在性，项目切换后清除不属于当前项目的结果。
- [UI 测试受 tkinter 和 Windows 环境影响] → 将展示状态和状态映射尽量设计为可独立测试的纯逻辑，并保留关键路径人工 GUI 验收与冻结程序冒烟测试。

## Migration Plan

1. 先扩展样式常量和可独立测试的展示状态映射，不改变现有菜单命令与业务服务。
2. 增加空状态和已打开项目工作台容器，将现有项目摘要、任务进度和日志逐步迁入新布局。
3. 将高频按钮接到现有共享命令，验证菜单和快捷键行为不变。
4. 接入任务结果持久展示、分层错误详情与日志折叠，并补齐状态矩阵自动测试。
5. 使用 `python -m doc_tool.app` 完成无项目、可写项目、只读项目、Word 不可用、任务成功/失败/取消等人工验证。
6. 运行现有测试与文档处理回归；实现完成后构建 PyInstaller onedir 并执行冻结程序冒烟测试，最终发布前再重建安装器。

回滚时可恢复原主窗口布局和样式文件；由于本变更不修改项目数据、应用服务协议或输出格式，回滚不需要数据迁移。若新结果区或折叠日志出现问题，可临时退回现有进度和完整日志布局，同时保留底层任务处理能力。

## Open Questions

- “打开报告”应优先定位最近一次任务报告，还是固定打开项目报告目录；实施时应依据现有服务已暴露的稳定路径选择，不为此新增业务格式。
- 日志折叠状态是否需要跨会话持久化；默认仅在窗口生命周期内保持，除非现有窗口状态存储可无兼容风险地扩展。
- 在 Windows 高对比度主题下，哪些自定义语义色需要退化为系统颜色；应在人工验收时确认。
