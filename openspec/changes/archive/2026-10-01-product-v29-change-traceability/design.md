## Context

V2.8 提供文档规范包、project schema v2、版本化评审与项目概览。现有 `traceability.py` 根据标题/编号及邻近正文提取关系，`BaselineStore.freeze` 快照主要覆盖 Markdown；不能据此承诺跨文档稳定关联和完整集合恢复。

## Goals / Non-Goals

**Goals:** 一个研发版本管理多份独立文档；关联/覆盖率/影响有依据；可用集合成果优先输出，完整基线不可变。遵循 `docs/product-flow-fallback-policy.md`，部分失败不停止全部出稿/恢复，严格交付显式选择。

**Non-Goals:** 测试执行平台、实时多人编辑、全 ALM、服务器权限/电子签章、AI 自动推断关联、跨项目任意 INCLUDE、自动更新下游正文、原地覆盖工作区恢复。

## Decisions

### D1：工作区作为外层清单

新增 `workspace.yml` schema 1：workspaceId、name、releaseVersion、documents（projectId、role、relative project path）、relationsPath。一个文档仍是独立 project.yml，可脱离工作区打开。首版工作区只引用根目录内项目，拒绝路径穿越和符号链接越界；添加外部项目时复制成新项目并给新 projectId，避免身份冲突。

role 为 requirement/design/test/reference，可先仅添加现有设计/测试文档，无需求时覆盖率 N/A；严格研发集合策略可要求主需求。允许同角色多份，重复项目/路径运行时去重并提示。缺失/非法成员不读取，其他成员仍可编辑/导出。releaseVersion 与各文档版本独立，UI 复用现有编辑器。

### D2：稳定身份独立于显示编号

首版稳定标记紧邻标题：`<!-- DOC-ITEM: id=<uuid> kind=requirement key=REQ-023 -->`，kind 可为 requirement/design/interface/test/acceptance，key 为可读别名，UUID 是身份。主键为 (projectId,itemId)，全工作区别名重复需提示并在关联选择中显示来源。

编辑器动作创建标记，复制条目时生成新 UUID，重命名/移动/重编号保留原 UUID。未标记内容不自动进入需求覆盖率分母。对旧编号启发式生成迁移建议表，展示路径、条目、建议关联和歧义；用户选择后原子写入标记/关系，不能仅凭相同“3.1”自动关联。

### D3：显式关系可审查

工作区 `trace/relations.yml` 进入版本控制，schema 1、relationId、source/target 项目与条目 ID、type、createdAt。type 首批为 satisfies（设计→需求）、verifies（测试/验收→需求或设计）、depends_on（同/跨文档依赖）。重复边拒绝，指向不存在端点保留为 dangling 错误；depends_on 循环保留但报告，影响遍历使用 visited 不死循环。

评审/复核记录可附在版本化工作区状态文件，记录 relationId、两端已确认 hash、复核时间与说明。缺少可信身份系统时操作者是本地声明的审查信息，不承诺法律签章或访问控制。

### D4：矩阵与影响必须可解释

覆盖率分母=用户明确纳入的 requirement 条目；设计覆盖=至少一条有效 satisfies 边；测试覆盖=直接 verifies 需求或沿该需求有效设计的 verifies 边。展示直接/间接证据，草稿/待复核计入“已关联”但不计入“已复核”，零需求显示 N/A，不显示 100%。未关联需求、孤立设计、重复 ID、悬空关系独立列表。

内容 hash 来自条目正文和相关资源 hash，不含显示编号/路径等纯位置变化；标题语义变化算内容变更。基于边计算直接和传递影响，显示路径、旧/新 hash 与原因，上游删除同样触发。项目模板/变量/规则变化生成文档级交付影响，不冒充所有需求语义变化。复核记录确认的是两端当前 hash；再次修改重新失效，机器不得将下游标为通过。

首版 CLI：`trace --workspace <dir> --output json|csv|md`、`impact --workspace <dir> --baseline <id> --output json|md`；同一关系图供 GUI/CLI/导出，状态和排序确定。

### D5：完整基线采用集合事务

`releases/<baseline-id>/` 保存 workspace/project manifests、正文、图片/复杂表资源、规范包、规则/术语、关系、评审/复核、检查/审计、正式 DOCX、应用版本和每文件 SHA-256。复用已有快照读取/差异方法，补齐资源与输出缺口；历史记录迁为 legacy-partial，禁止假称可完整恢复。

创建：获取工作区租约和按 projectId 排序的项目锁→复制并校验本次输入快照→在准备目录构建文档并检查→形成结果/缺失清单→完整可登记的集合原子提交，其余保留独立可读结果。构建始终读取已固定快照，不将后来的源修改混入其中；现有单项目正式输出由原服务维护，集合不得覆写已有版本。

上述完整登记与“生成可用集合”分开。默认从准备目录中的固定输入快照构建；外部后来变动只提示快照时点，不要求作者重跑。复制快照期间输入不一致可刷新一次，仍无法稳定的成员跳过。个别成员/资源不可用或检查不满足时输出可用成员、说明占位与缺失清单，状态 partial/待刷新/待登记、complete=false，不冒充完整正式基线；支持后续补齐。重复集合版本默认先另存唯一快照并建议新版本，旧集合不覆盖。严格策略失败也保留可读成果；用户取消不继续后台出稿。

不强制作者退出编辑：仅在复制本次快照期间获取必要锁/核验 hash，固定快照后编辑可继续。现有锁不通过界面 disabled 替代，对资源读取/ZIP 导出校验路径边界。

### D6：恢复生成新工作副本

基线只读。完整恢复校验文件及 hashes；默认对局部/损坏集合也允许将可验证内容恢复到安全新目录，跳过不可信/缺失文件并生成恢复清单，状态部分恢复。分配新 workspaceId/projectId，映射合法关系；悬空关系保留待处理且不计覆盖率，itemId 保留。目标已存在默认新目录名，不覆盖当前工作副本或旧集合；只有没有可恢复内容/无法写副本时才停止恢复。原始清单另存供补齐。

## Risks / Trade-offs

- [跨项目锁与资源变动产生半份交付] → 固定锁顺序、准备目录、输入复核与集合原子提交。
- [启发式自动匹配制造假覆盖率] → 显式 ID/边，迁移建议人工确认，覆盖率展示分母与证据。
- [snapshot 占用空间] → 先完整正确，提供体积统计及手动导出清理；去重存储另行优化。
- [大量条目 UI 卡顿] → 增量 hash、后台图计算、表格分页；性能基准随夹具记录。

## Migration Plan

单文档项目默认不变；新建工作区后显式添加。先只读旧追踪再迁移 ID/关系，备份保留。V2.8 意见按已确认定位映射，歧义待复核。旧 Markdown-only 基线可查看/导出/部分恢复，缺失资源清单可见；只有验证齐全的新完整快照标完整恢复。

## 验收标准

- A29-1：需求/设计/测试三项目加入同一工作区，独立打开仍正常；目录复制后可解析。
- A29-2：重排、改编号、移动条目后关系保持，复制产生新 ID；同号跨文档不误关联。
- A29-3：多对多、零需求、悬空关系、循环依赖与缺失端点的覆盖率/错误输出一致。
- A29-4：上游修改/删除触发直接与传递影响，复核后再次修改重新待复核；单纯路径变化不虚报。
- A29-5：成员失败/缺资源仍输出部分集合与清单；后续源变化不撤销一致输入快照成果，完整/部分状态分明，取消和旧基线保护正确。
- A29-6：完整集合恢复资源/关系齐全，损坏/旧局部集合可恢复合法部分并给清单，目标冲突自动新目录，原副本/历史不变。

## Open Questions
