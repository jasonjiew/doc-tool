## Context

章节树由 `doc_tool/application/content/tree.py` 从 rel_path 列表推导，编号来自文件名数字前缀（`3.7.5 设备管理.md`），目录名也携带编号段；`next_chapter_rel_path` 与 `renumber_plan_after_delete` 已实现“新章节取最大兄弟编号 +1”和“删除后同级递减重编号”。引用联动由 `refactor.py` 提供：`compute_rename_plan` 生成单文件 dry-run（章节号引用、链接、自身标题行），`apply_rename_plan` 经 `ContentWriter` 备份 + 改动清单写回并可回滚。UI 侧 `tree_panel.py` 的 `QTreeView` 目前是只读模型（`flags` 仅 enabled/selectable），支持键盘、右键、筛选与定位联动。

Word 构建在 `scripts/build_docx.py`，当前只支持标题、表格、图片、段落与占位空段；无序/有序列表只是“段落加符号前缀”，不生成 `numPr`/`abstractNum`；不支持超链接、书签、行内粗体/斜体/代码与脚注。`validate_docx.py` 用事件流对比与模板保留校验保证可重复构建。

本变更分两阶段：先做内容层的拖拽重排（纯数据 + 服务层 + UI 接线），再做构建层的 Word 表达扩展。两者都不得改变项目格式与既有文档语义。

## Goals / Non-Goals

**Goals:**

- 章节树支持文件节点同目录排序与跨目录移动，目录节点拖拽移动整棵子树。
- 移动后按目标目录规则自动重编号，并在应用前给出引用联动影响的 dry-run 预览。
- 批量移动复用现有备份/改动清单/回滚机制，任意失败整体回滚。
- 构建层支持超链接、标题书签与锚点、粗体/斜体/行内代码、真实多级列表与脚注。
- 校验层识别新表达元素，保持事件流对比与模板保留语义。
- 覆盖正向与边界场景的自动化测试与人工验收。

**Non-Goals:**

- 不引入排序元数据字段，不改变“编号由文件名前缀推导”的既有模型。
- 不做跨文档类型的无条件合并；跨类型移动默认拒绝（当前无配置项），按目标类型规则重编号留作后续增强。
- 不在本变更实现批注、修订、公式与图表；仅记录评估入口。
- 不改变 `project.yml`、Markdown 语法基线、输出状态与原子发布语义。
- 不引入新的 Markdown 方言或第三方 md→docx 转换库。

## Decisions

### 1. 拖拽重排 = 物理移动文件 + 引用联动，而非排序元数据

章节编号由文件名前缀推导、全系统以 rel_path 为键，因此拖拽排序/移动必须物理重命名文件并更新引用。内容层生成“旧→新 rel_path + 引用编辑清单”的计划，UI 确认后批量应用。备选方案“仅记录显示顺序”会与最终 Word 目录、章节号引用全部脱节，排除。

**Alternatives considered:**

- 引入排序元数据字段：破坏编号推导与 `build_tree` 排序，且与 Word 目录不一致。
- 仅改树显示顺序：文件系统与正文引用不变，无法满足“结构调整”的真实需求。

### 2. 批量移动计划由多个单文件计划组合，先算后写

把 `renumber_plan_after_delete`/`next_chapter_rel_path` 的编号推导推广为“移动 + 插入 + 删除”通用的重编号推导，再把 `refactor.py` 的 `RenamePlan` 扩展为可聚合多文件重命名与全部引用编辑的批量计划。计划先按目标编号排序保证无冲突（每个目标号恰是上一步让出的槽位），再统一应用。备选“逐文件即时应用”会在中途失败时留下中间态，排除。

**Alternatives considered:**

- 逐文件即时应用：失败时难以整体恢复。
- 构建独立的新事务层：与 `ContentWriter` 备份/回滚机制重复，扩大改动面。

### 3. dry-run 预览作为应用前置门槛

拖拽释放后先计算计划并展示“受影响文件数、引用改动条数、编号冲突与悬空风险”，用户确认后才写盘；取消即丢弃计划。这延续现有重命名确认交互，并让引用影响对用户透明。备选“直接应用 + 撤销”需要额外的撤销快照与跨界面一致，成本高，排除。

### 4. 拖放交互在现有 QTreeView 上实现

在 `tree_panel.py` 的 `_ChapterTreeView` 启用拖放：模型声明可拖拽/可放置 flags 并提供 `dropMimeData`，视图按释放位置判定“目录内追加 / 文件前插入 / 非法目标”。目标判定与编号推导都放在内容层（可单测），UI 只做交互与确认。

**Alternatives considered:**

- 系统文件管理器式外部拖放：无法展示引用联动预览，也无法复用内容层计划。
- 菜单驱动的“移动到…”：交互步骤多，不适合频繁重排。

### 5. Word 表达扩展在现有解析/渲染管线内增量实现

在 `build_docx.py` 的 `process_markdown` 中新增行内标记（`**`/`*`/`` ` ``）、链接、列表、脚注解析，产出新的中间 token；渲染阶段在 `append_text`/`make_paragraph` 基础上生成 `w:b`/`w:i`/等宽 run、`w:hyperlink`、`numPr`/`abstractNum`、`w:footnote`。继续复用现有 run 与段落生成器，避免第二条渲染路径。

**Alternatives considered:**

- 注入模板 OOXML 片段：与事件流对比校验冲突，且模板保留校验难保证。
- 引入第三方 md→docx 库：改变构建内核、模板保留语义与依赖面，风险高。

### 6. 多级列表用样式化 numPr/abstractNum，按首项编号起点

列表渲染为真实编号：`-`/`*` 映射项目符号，`N.`/`N、` 映射有序编号，缩进层级映射多级 abstractNum；有序列表以作者首项编号为起点，被普通段落分隔后新建列表实例。渲染使用样式化编号而非内联覆盖，降低对模板样式的影响。

**Alternatives considered:**

- 继续段落符号前缀：不满足“真正的多级列表”。
- 手写 numId 且不按样式：破坏模板编号签名，校验难通过。

### 7. 校验扩展沿用事件流 + 语义检查单一通道

在 `validate_docx.py` 中把超链接、书签、列表、脚注纳入事件流对比与语义检查（书签唯一、链接目标存在、列表 numId 有效、脚注引用与定义计数一致），不另建静态检查通道，避免两套校验口径。

**Alternatives considered:**

- 单独静态检查脚本：与现有校验口径重复且容易漂移。

## Risks / Trade-offs

- [批量移动在回滚失败时留下部分移动状态] → 应用前生成完整备份，回滚按逆序执行；改动清单先落盘再操作，失败时按清单恢复。
- [真实编号列表改变既有文档渲染，可能触犯模板编号保留校验] → 用样式化 numPr 而非内联覆盖；扩展校验的编号签名比较，先对照模板编号样式验证。
- [超链接/书签引入后与 Word 刷新（refresh_fields）相互影响] → 刷新只更新域（TOC/PAGEREF/NUMPAGES），不触碰超链接关系；发布后校验确认无损坏关系。
- [行内格式解析与 `<br>`、表格内文本、现有段落指令冲突] → 解析阶段先按行内标记拆分 run，表格单元格与段落共用同一 run 渲染路径。
- [脚注增加文档体积与校验复杂度] → 脚注集中于 `footnotes.xml`，校验检查脚注与正文引用计数一致、目标存在。
- [拖放误操作导致章节号大规模变化] → 强制 dry-run 预览 + 冲突标注 + 只读禁用；预览显示受影响文件数，降低误操作代价。

## Migration Plan

1. 先扩展内容层：在 `tree.py` 实现通用的移动/插入重编号推导与目录子树移动推导，在 `refactor.py` 实现批量计划与批量应用/回滚，并为计划推导补充单测。
2. 在 `tree_panel.py` 接入拖放：目标判定、非法目标拦截、预览确认对话框、应用回调与刷新。
3. 内容层与 UI 联调：应用后重建索引与树，保持选中/展开与当前文件定位稳定。
4. 构建层增量扩展：行内格式 → 多级列表 → 超链接/书签 → 脚注，逐项提交并跑构建用例。
5. 扩展 `validate_docx` 的事件流与语义检查，回归既有文档构建与校验。
6. 人工验收：拖拽重排典型路径与 Word 打开验证链接/书签/列表/脚注/行内格式。
7. 全量自动化测试 + PyInstaller 构建冒烟，确认冻结态拖拽与构建正常。

回滚策略：内容层与 UI 改动可通过还原 `tree_panel.py`/`tree.py`/`refactor.py` 撤销；构建层改动按“行内格式→列表→链接/书签→脚注”逐项回退。本变更不修改项目数据格式，回滚无需数据迁移；若列表渲染带来校验回归，可临时回退到段落前缀渲染并保留新解析 token。

## Resolved Questions

> 原 Open Questions 四项均已由实现决出，归档前关闭。

- 跨文档类型移动默认策略 → **一律拒绝**。当前无项目配置项：源与目标均为显式文档类型时，内容层抛「不允许跨文档类型移动」，UI 展示拒绝原因；`chapter_move_renumber_plan` 的 `allow_cross_type` 参数仅预留，UI 不传。允许跨类型按目标规则重编号留作后续增强。
- 有序列表起始编号与续号 → **首项编号作为实例起点**（`parse_list_line` 取首项数字，`NumberingManager.new_list(kind, start)` 写入 `w:start`）；无显式续号语法，列表被普通段落分隔即新建实例（不强制续号）。
- 站内链接 Word 端表达 → **`w:hyperlink` + 书签锚点**（`w:anchor`），外部 URL 用带 `r:id` 的外部 `w:hyperlink`；书签由 `w:bookmarkStart/End` 承载，刷新域（TOC/PAGEREF/NUMPAGES）不受影响。
- 批注/修订/公式/图表 → **本变更不实现**（见 Non-Goals），语法形态待核心五项落地后基于使用反馈评估。
