## Context

当前仓库已经拥有完整的大文档导入、Markdown 编辑、资源管理、质量检查和 Word 重建链路，`general` 也是默认项目类型；专用化主要集中在品牌常量、导入预设、项目类型枚举、质量规则、根目录内置文档、打包数据收集和发布命名上。与此同时，项目 schema v1、内容索引和大量测试已经认识 `requirement` / `design`，直接删除枚举会使已有项目无法加载，并产生不必要的数据迁移风险。

公共发行还面临比代码改名更严格的边界问题：仓库根目录包含公司模板、真实业务 Markdown、图片和复杂表格，当前 PyInstaller spec 会收集 `templates/` 与 `config/`，CI 和安装器也携带公司名称、内网发布假设与稳定 AppId。仅在工作树中删除这些文件不足以清除历史泄漏，因此实现完成与“允许公开”必须由独立门禁区分。

本变更的利益相关方包括公共用户与贡献者、既有内部项目用户、发布维护者、著作权人/法务和安全审核人员。技术实现必须兼顾公共产品的简单模型与旧项目的连续可用性。

## Goals / Non-Goals

**Goals:**

- 将公共产品定位统一为通用大型 Word 文档工作台，消除面向用户的公司品牌与需求/详细设计预设。
- 新建项目只有一个稳定的通用路径，同时继续安全读取和构建 schema v1 的旧专用项目。
- 建立代码、资源和安装包的公共发行允许边界，使公司材料不会被隐式打包或发布。
- 将品牌、包名、安装路径、SBOM 名称和设置命名空间集中管理，避免再次散落硬编码。
- 为公开协作补齐最低治理文件和发布前自动/人工门禁。
- 保持导入保真、Markdown 编辑、搜索、恢复、质量检查和 Word 构建能力不退化。

**Non-Goals:**

- 本变更不把应用重写为跨平台或 Web 应用。
- 本变更不实现 LibreOffice 字段刷新后端；正式刷新仍可依赖 Windows Word。
- 本变更不删除追踪矩阵等可复用的高级能力，只去除其对公共产品类型的强制暴露。
- 本变更不自动决定许可证、著作权归属、商标授权或公开仓库地址；这些必须由权利人确认。
- 本变更不在原仓库内自动重写 Git 历史，也不把历史清理等同于普通文件删除。
- 本变更不保证任意 Word 无损往返，继续沿用现有保真报告和质量门禁边界。

## Decisions

### 1. 公共新建模型固定为 `general`，旧类型作为兼容值保留

`ProjectManifest` schema v1 继续接受 `general`、`requirement` 和 `design`，以免破坏已有项目；但公共导入向导和 CLI 始终创建 `documentType: general`。代码中区分：

- `CREATABLE_DOCUMENT_TYPES = ("general",)`：公共新建能力；
- `SUPPORTED_LEGACY_DOCUMENT_TYPES = ("requirement", "design")`：兼容读取能力；
- `READABLE_DOCUMENT_TYPES`：两者合集。

旧项目打开时保留原始路径和规则，不做静默原地改写，并在项目栏标注“旧版专用项目”。迁移命令必须先复制到新目录或生成可恢复备份，完成结构、资源与试构建校验后才提交。

**替代方案：立即删除 `requirement` / `design`。** 这会使 schema v1 项目加载失败，且需要同时重写目录、资源引用、质量配置和历史状态，风险与开源目标不成比例。

**替代方案：继续让用户选择三种类型。** 这保留了产品认知和代码中的业务耦合，不能形成简单的公共定位。

### 2. 文档元数据与业务预设解耦

文档名称仍为必填；文档编号与版本在通用项目中均为可选。输出命名函数必须对空编号/版本产生安全、可预测的文件名，不再以非 `general` 类型施加强制字段。

需求/设计特征识别从预检的产品模式建议中移除。标题样式映射、保真检查和源文档生成模板继续工作，因为它们与业务类型无关。专用质量规则若仍需要供内部项目使用，应通过兼容适配或未来私有 profile 包提供，而不是进入公共默认体验。

### 3. 集中公共品牌元数据

新增无 Qt 依赖的品牌/发行元数据模块，至少定义：显示名、程序标识、组织标识、可执行文件名、安装目录段、CLI 名和公共 URL 占位策略。GUI、CLI、日志、安装器生成、SBOM 和测试从同一源或经构建脚本同步校验。

首版使用：

- 显示名：`Doc Tool`；
- 程序标识/可执行文件：`DocTool` / `DocTool.exe`；
- CLI：`doc-tool`；
- 组织设置键：中性且稳定的 `DocToolProject`（最终公开名称确定前可调整一次）。

Inno Setup 的稳定 AppId 必须为公共产品生成新的值，不复用公司产品 AppId。旧安装与公共安装可并存；设置迁移只读取旧命名空间中的窗口几何、主题、最近项目等非敏感偏好并复制到新命名空间，不删除旧值。

**替代方案：在每个文件中机械替换字符串。** 容易遗漏 CI、SBOM、测试和未来新增入口，无法建立一致性门禁。

### 4. 公共发行采用显式允许清单

公共 PyInstaller spec 不再遍历并收集仓库根 `templates/`、`config/`、`content/` 或 `assets/`。运行必需的默认资源必须放在 `doc_tool/resources/` 下并逐项列入 spec；示例项目放在独立 `examples/` 中，默认不进入安装包，除非经过允许清单审核。

公共仓库应从一个没有敏感历史的新仓库或净化导出构建。发行扫描至少阻断：

- 公司品牌和已知内部文档编号；
- RFC1918 内网 URL/IP 和内部域名；
- 非允许位置的 DOCX、图片、OOXML 表格和配置；
- 密钥、证书、令牌及常见凭据格式；
- 安装包中未登记的顶层资源。

扫描目标包括 Git 跟踪文件、构建数据清单、`dist/` 和 Release 产物。扫描允许清单必须精确到路径和目的，不能使用宽泛目录豁免。

### 5. 示例与测试使用全新虚构语料

不能只对真实业务内容做姓名替换。示例 Word、Markdown、图片、复杂表格和测试期望值应从零创建，采用虚构主题（例如“星河知识库用户手册”），不复用公司章节、系统代号、设备型号、截图布局或文档编号。

测试应覆盖通用项目的导入、编辑、搜索、资源、构建、安装与泄漏扫描，同时保留最小的合成旧项目夹具来验证 `requirement` / `design` 兼容；旧夹具只能含人工构造文本。

### 6. 产品界面围绕单项目而非业务类型组织

通用项目的内容根就是项目自身的章节集合。章节树直接从章节点开始，不额外显示“通用大文档”类型根；搜索和替换默认覆盖当前项目全部 Markdown，不显示类型复选框。

旧版多类型布局继续显示类型根并允许兼容筛选。该判断来自索引结构/清单兼容状态，不通过标题文本猜测。问题中心中的 `documentType` 可继续作为内部诊断字段，但新项目默认固定为 `general`，界面无需把它作为主要筛选维度。

### 7. 治理与发布授权是正式 Release 的硬门禁

公共仓库必须包含可机器识别的 OSI 批准许可证文本、`CONTRIBUTING.md`、`CODE_OF_CONDUCT.md`、`SECURITY.md`、Issue/PR 模板和准确的第三方许可证说明。许可证持有人和年份必须来自书面权属决策，实施人员不得猜测。

在权属、品牌和许可证仍未决时，可以完成代码通用化和私有 beta 构建，但 CI 必须拒绝生成标记为“public release”的产物。发布检查清单需要记录批准人、Git 历史扫描结果、干净环境复现结果及安装/卸载验证。

## Risks / Trade-offs

- **[旧项目兼容逻辑长期存在，增加维护面]** → 将兼容值集中隔离，新增项目不再产生旧类型，并为未来 schema v2 迁移设定删除条件。
- **[品牌改名造成设置和最近项目丢失]** → 首次启动只读迁移旧 QSettings 命名空间，写入新命名空间后以测试验证，保留旧数据便于回滚。
- **[移除根模板后冻结构建缺少运行资源]** → 用允许清单测试断言实际导入/构建所需资源，并在干净冻结应用中运行端到端冒烟测试。
- **[机械脱敏遗漏 OOXML、图片或 Git 历史内容]** → 从零创建公开示例，扫描 ZIP/OOXML 内部文本与二进制元数据，并从净化仓库发布；保留人工复核门禁。
- **[公共名称 `Doc Tool` 过于通用或发生商标冲突]** → 品牌集中化使后续更名成本可控；正式 Release 前完成名称检索和授权确认。
- **[许可证与依赖不兼容]** → 在确定主许可证后生成依赖许可证矩阵，审查 PySide6/Qt 与安装分发义务，并让法律/合规确认。
- **[专用质量能力被错误删除，降低内部可用性]** → 先隐藏公共入口并保留兼容适配；公司专用规则迁移到私有扩展后再评估底层删除。
- **[README 宣称已开源但授权尚未完成]** → 授权和 LICENSE 未齐备时保持“preparing”状态，发布作业必须阻断正式开源标签。

## Migration Plan

1. 冻结并记录当前内部版测试基线、应用版本、schema 与安装器 AppId。
2. 引入集中品牌元数据和公共包名，但暂不删除旧设置；补充品牌一致性与设置迁移测试。
3. 将 UI/CLI 新建路径固定为 `general`，保留旧清单加载与构建测试；实现显式、可回滚的旧项目迁移工具或指导。
4. 从冻结 spec 和发布脚本移除根模板/配置的隐式收集，建立运行资源允许清单和公共发行扫描。
5. 用全新虚构夹具替换测试与示例；执行全量测试、冻结冒烟、安装/卸载和 Word 实机验证。
6. 在单独的净化公共仓库中只迁移批准内容，不携带原 Git 历史；运行历史、凭据和敏感标识扫描。
7. 获得书面开源授权并确定许可证、品牌、维护与安全联系方式后，补齐治理文件和真实公共 URL。
8. 先发布预发行版本，验证旧项目兼容与通用导入，再发布首个稳定公共版本。

**回滚策略：** 品牌和公共安装使用新 AppId/目录，不覆盖内部安装；旧项目不被原地迁移；任何发布门禁失败即停止公共 Release。代码回滚后原内部应用仍可读取未被改写的旧项目和设置。

## Open Questions

- 最终公共项目名称、组织标识、图标和域名是什么，是否完成商标检索？
- 著作权主体是公司还是个人，谁有权签署开源授权并选择许可证？
- 主许可证选择 Apache-2.0、MIT、MulanPSL-2.0 或其他 OSI 许可证中的哪一个？
- 公共版是否承诺长期构建旧 `requirement` / `design` 项目，还是只提供一个过渡发布周期？
- 公司专用质量规则未来采用独立私有插件、私有分支，还是完全停止维护？
- 公共 CI 最终托管于 GitHub Actions、GitLab.com 还是其他平台？
