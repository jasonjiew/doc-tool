## Context

当前工程已经具备经过验证的 DOCX 构建、严格校验、Word 字段刷新以及从固定原 Word 提取内容的脚本。日常合并入口依赖仓库相对目录、固定的 `requirement/design` 配置和外部 Python 环境；迁移脚本又把源文件名写在代码中，并直接写入固定的 `content/assets/templates`。这种形态适合单项目研发验证，不适合将安装包直接交给团队成员。

目标用户主要是 Windows 办公终端上的产品、需求、研发和文档维护人员。他们不应安装 Python 或理解脚本参数，只需要导入符合公司 Word 体系的 DOCX、编辑拆出的 Markdown、执行校验和合并。正式输出必须继续使用本机 Microsoft Word 刷新 TOC、页码和总页数；应用不得在无人值守服务器环境运行 Word COM。

源码、测试和打包脚本进入公司私有 Git。真实项目数据独立存放，可按项目选择是否进入另一个受控文档仓库。安装目录、应用缓存和用户项目数据必须分离。

## Goals / Non-Goals

**Goals:**

- 为任意合法文件名的公司需求/详细设计 DOCX 提供安全、可重复、失败不留半成品的首次导入与章节拆分。
- 用一个 Windows 桌面程序覆盖新建/打开项目、拆分、打开内容目录、校验、合并、查看日志和打开输出的完整工作流。
- 复用现有 OOXML 构建和校验实现，通过项目上下文消除固定路径与固定文件名。
- 生成团队成员可直接安装的单个 Setup EXE，运行时不依赖系统 Python。
- 使用 Git 标签触发可复现的测试、打包、安装冒烟和 Release 发布，并提供版本、哈希和可选代码签名。
- 保证软件升级、降级和卸载不修改用户项目；旧版命令行项目在迁移后仍可构建。

**Non-Goals:**

- 不实现多人同时编辑同一个本地项目的实时协作编辑器；协作由 Git 或受控同步流程承担。
- 不承诺从没有 Word Heading 样式、仅靠手工加粗和手输编号的任意 DOCX 自动推断出正确章节树。
- 不在服务端、Windows 服务或计划任务的非交互会话中自动启动 Microsoft Word。
- 不把 Markdown 编辑器完整内嵌到首版应用；应用负责打开项目目录，成员使用既有编辑器维护内容。
- 不在首版实现自动在线更新；Release 页面和版本检查可作为后续增强。

## Decisions

### 1. 采用“薄 GUI + 应用服务 + 现有文档内核”的分层架构

桌面应用使用 `tkinter/ttk` 提供轻量 GUI，界面只负责收集输入、展示状态和调用应用服务。应用服务负责项目生命周期、事务、进度和错误模型；文档内核继续负责 DOCX 提取、构建、校验和 Word 刷新。

建议模块边界：

```text
doc_tool/
├─ app.py                     GUI 入口
├─ ui/                        页面、对话框、后台任务桥接
├─ application/               import/build/validate/open-folder 用例
├─ domain/                    ProjectManifest、ProjectPaths、结果与错误
├─ adapters/                  OOXML、Word COM、文件系统、日志
└─ resources/                 默认配置、图标、安装级说明
```

现有脚本保留为 CLI 适配层，调用同一应用服务，而不是让 GUI 启动并解析多个脚本输出。这样既保留自动化测试入口，也避免 GUI 和命令行出现两套业务逻辑。

备选方案是使用 PySide6。它能提供更丰富的界面，但会显著增加安装体积、打包复杂度和许可审查；首版工作流简单，`tkinter/ttk` 足够且随 Python 分发，因此选用后者。

### 2. 每个文档项目使用自包含、带模式版本的工作区

项目默认创建在用户选择的目录，而不是安装目录。规范结构为：

```text
<project>/
├─ project.yml
├─ original/source.docx
├─ template/template.docx
├─ content/<document-type>/...
├─ assets/<document-type>/images/...
├─ assets/<document-type>/tables/...
├─ output/...
├─ logs/...
└─ .state/project.lock
```

`project.yml` 至少包含 `schemaVersion`、稳定 `projectId`、文档类型、文档编号/名称/版本、相对路径、源文件 SHA-256、创建/最近成功构建版本，以及 Word 刷新超时。所有持久化路径必须相对项目根，禁止把安装机器绝对路径写入可共享配置。

`ProjectPaths` 负责解析和约束路径，任何资源解析后都必须仍在项目根内。项目模式升级前创建清单备份，并以幂等迁移逐版本升级。

### 3. 首次导入采用暂存事务和原子发布

导入流程：

1. 用户选择 DOCX、文档类型、项目名称和目标父目录。
2. 预检扩展名、ZIP/所有 XML、关系目标、是否存在 Heading 1、Heading 1~3 映射、目标目录冲突和磁盘可写性。
3. 在目标父目录创建唯一暂存目录，复制原文件并计算 SHA-256；后续永不修改用户选择的原文件。
4. 从暂存副本生成模板骨架，提取正文、图片和复杂表格，再生成编号连续的目录树与 `_index.md`。
5. 写入项目清单，运行结构、资源和一次试构建校验。
6. 全部通过后，将暂存目录原子重命名为最终项目目录；失败时保留诊断日志并删除/隔离暂存目录，不发布项目。

若目标项目已存在，首版必须拒绝覆盖并要求另选名称；“重新导入并合并差异”不是首次导入的隐式行为。这样避免再次导入破坏已经维护的 Markdown。

### 4. 标题识别以 Word 样式为事实来源，自动识别失败时阻断

导入器从 `styles.xml` 建立 styleId 到 Heading 级别的映射，并以正文段落的样式确定 H1~H3，而不是仅解析可见编号。文档类型优先由用户选择；应用可依据文档编号、封面关键字段和已知样式给出建议，但不得在置信度不足时静默决定。

导入预览显示各级标题数量、首尾若干标题、图片/表格数量以及告警。没有 H1、层级跳跃、关系损坏、加密/非 DOCX 或标题树无法闭合时失败并给出修复建议。手工样式映射可作为后续版本能力，首版不猜测正文中的编号文本。

### 5. 合并继续使用经过验证的四阶段门禁

桌面“合并生成 Word”调用：

```text
章节与资源预检
  → 临时文件构建 DOCX
  → 刷新前严格校验
  → Microsoft Word 专用交互式进程刷新 TOC/页码/NUMPAGES
  → 刷新后严格校验
  → 原子替换 output 中的正式产物
```

正式模式检测不到 Word、Word 刷新失败或刷新后校验失败时，操作整体失败且不覆盖上一次有效输出。诊断模式可以跳过 Word，但界面必须把结果标为“非正式构建”，不能与正式成功使用相同状态。

应用继续使用专用 `DispatchEx` Word 进程，不复用或结束用户已打开的 Word。单项目通过锁文件和进程标识禁止并行导入/构建；不同本地项目可以并行，但首版 GUI 一次只运行一个后台文档任务。

### 6. GUI 长任务在后台线程运行并使用结构化事件

导入和合并不得阻塞界面线程。应用服务发出 `stage/progress/warning/error/result` 事件，GUI 显示当前阶段和日志摘要。取消只在阶段边界生效；一旦进入 Word 保存或原子发布临界区，界面显示“正在完成安全保存”并延迟取消，避免产生损坏文件。

错误对象包含稳定错误码、用户说明、建议操作和日志路径。日志记录时间、版本、阶段、文件哈希、计数和异常栈，不记录正文、表格单元格内容或图片数据。默认日志轮转并允许用户一键打开日志目录。

### 7. 使用 PyInstaller onedir，再由安装器封装为单个 Setup EXE

PyInstaller spec 文件显式收集模板、默认配置、图标、许可文件以及 `lxml/Pillow/pywin32` 隐式依赖，产出目录式应用包。Inno Setup（或公司批准的等价安装器）将该目录封装为一个 `KonsungDocTool-Setup-<version>.exe`。

应用默认按用户安装到 `%LOCALAPPDATA%\Konsung\DocTool`，无需管理员权限；创建开始菜单快捷方式和可选桌面快捷方式。应用资源通过统一 `resource_root()` 解析，开发态读取仓库资源，打包态读取 PyInstaller 资源目录。任何用户项目不得默认建立在安装目录下。

选择 onedir 而不是直接 onefile，是为了减少每次启动解压、杀毒软件扫描、动态库加载及大体积模板资源定位的不确定性；对用户而言安装器仍然是单个 EXE。

### 8. Release 构建必须来自干净的 Windows CI 和版本标签

`vX.Y.Z` 标签触发以下流水线：

1. 检查版本号与标签一致，安装锁定的构建依赖。
2. 运行单元、破坏性校验、导入/迭代和既有双文档回归。
3. 在 Windows Runner 构建 PyInstaller onedir。
4. 在干净临时目录运行冻结程序的无 Word 冒烟测试。
5. 编译安装器，静默安装到测试目录，执行启动/项目创建/卸载不删项目的安装级冒烟。
6. 如配置证书则签名程序与安装器；始终生成 SHA-256 清单和 SBOM/依赖清单。
7. 将安装器、哈希和发布说明上传到私有 Git Release。

打包脚本放在 `packaging/` 并可在开发机复现；CI 配置只负责编排，避免把构建逻辑锁死在 GitHub/GitLab 某一家平台。

### 9. 升级和卸载只管理应用文件

安装器使用稳定 AppId，升级前结束本应用自身进程并替换安装目录。用户项目、外部 Git 工作区和日志导出目录不登记为安装器拥有的文件，因此卸载不会删除。应用启动时发现更高项目模式版本必须拒绝写入并提示升级；发现较低模式版本则先备份清单再执行受测迁移。

回滚应用版本时，旧版可以打开模式兼容的项目；不兼容时只读展示并提示恢复迁移前清单或重新安装新版本，不做破坏性降级迁移。

## Risks / Trade-offs

- [源 Word 未正确使用 Heading 样式，自动拆分错误] → 导入前展示标题树摘要并 fail-closed；首版不依据视觉加粗猜层级。
- [再次导入覆盖已维护 Markdown] → 首次导入只允许创建新目录；未来差异导入必须作为独立、有预览和备份的功能设计。
- [Word COM 卡死或弹出交互框] → 禁用宏和提示、使用专用进程与超时、只终止本次进程、失败不替换正式输出。
- [杀毒软件拦截未签名 Python 冻结程序] → 采用目录式包、公司代码签名、私有 Release、SHA-256 和试点白名单；不通过关闭安全软件绕过。
- [安装包体积较大] → 接受以换取零 Python 环境依赖；在可复现性验证后再评估排除无用模块。
- [同步盘或网络盘多人并行导致冲突] → 建议每人本地 Git 工作区；项目锁只解决单机并发，不宣称跨机器分布式锁。
- [应用升级与项目模式不兼容] → 版本化清单、迁移备份、向前版本拒写和安装器回滚包。
- [长文档导入/合并耗时且界面像卡死] → 后台任务、阶段进度、心跳日志和安全取消边界。
- [真实文档进入源码 Release] → 构建清单只包含净化模板/测试夹具，CI 检查禁止 `projects/`、`output/` 和生产 DOCX 进入安装包。

## Migration Plan

1. 先引入 `ProjectManifest/ProjectPaths`，让现有 CLI 可通过 `--project` 使用新项目，同时保留当前 `requirement/design` 入口作为兼容层。
2. 将迁移脚本重构为无固定文件名、无全局目录副作用的导入服务，并补齐事务、标题预检和导入回归。
3. 为当前已验证的需求/详细设计创建项目清单，通过新旧入口生成结果对比，确认结构、业务内容和模板语义不变。
4. 增加 GUI，先发布内部便携测试包，使用两份基线文档和至少一份新公司文档试点。
5. 增加 PyInstaller、安装器和 CI Release，验证无 Python 的干净 Windows 终端、Word 存在/缺失、升级、回滚和卸载场景。
6. 发布 `1.0.0` 前保留现有 `.cmd` 入口作为故障回退；团队稳定使用两个版本后再评估是否仅保留高级 CLI。

回滚策略：停止分发问题 Release，重新发布上一已签名安装包；用户项目不随应用卸载，必要时恢复 `project.yml` 迁移前备份。任何回滚不得用旧应用写入其不理解的更高模式项目。

## Open Questions

- 公司实际使用 GitHub Enterprise、GitLab、Gitee 还是其他私有 Git，决定最终 Release 流水线适配文件。
- 是否已有 Windows 代码签名证书和安全软件白名单流程；没有证书时首版只能作为受控试点包。
- 首版明确支持的 Windows、Office 位数和版本矩阵需要由团队基础环境确认。
- 真实项目 Markdown 是否单独进入文档 Git 仓库，还是由现有文档管理系统托管，需要确定权限与保密策略。
