# 修订评审功能方案

> 版本：v2（2026-09-03）
> 定稿输入：评审纪要表确认为 **9 列**标准表——序号 / 提出人 / 评审问题 / 责任人 / 计划完成时间 / 更改确认 / 评审记录 / 更改结果与证据 / 遗留问题（两行表头）；最终《评审纪要》由工具直接生成（DOCX / Markdown）。
> 本文件用于方案对比；确定后按 openspec 变更流程推进（`openspec/changes/revision-review-export/`）。

---

## 1. 背景与目标

**问题**：文档改动完成后要开评审会，会议室无法安装本工具，评审对象必须是离线的 Word 文档；会后意见要回到工具逐条处理、确认，并沉淀为公司标准格式的《评审纪要》；全部意见处理完之前不应允许发布正式稿。

**目标**：

1. 一键导出**只含改动章节**的会议评审稿（Word），会议现场可打印/投屏使用；
2. 会议产生的意见（按公司 9 列评审纪要表格式）**回流工具**，逐条处理、确认；
3. 闭环后工具**直接输出正式《评审纪要》**（9 列表，DOCX / Markdown），供归档与走签批；
4. **发布门禁**：存在未解决（或未更改确认）意见时阻断发布，保证「评审过 → 改完 → 确认过」才出正式稿。

## 2. 现状基础（全部可复用，不新增依赖）

| 现有能力 | 模块 | 本方案中的角色 |
| --- | --- | --- |
| 会话基线 diff（增/改/删 + 重命名归并），发布成功后自动重置 | `content/snapshot.py`、`content/changes.py`、`pipeline._refresh_content_baseline` | 评审稿的「改动点」口径，与改动面板/章节树徽标完全一致 |
| Markdown → 排版 HTML → Word DOCX（宋体/Times、标题层级、表格边框、图片内嵌）；Word 不可用有稳定错误通道 | `markdown_word.py`、`convert.py`、`adapters/word_convert.py` | 评审稿、评审纪要的渲染与出稿链路 |
| 意见存储（绑章节+行号）、签字、审批门禁、json 评审包 | `review/review_store.py`、`approval_gate`、`ReviewPackageBuilder` | 闭环的数字载体，扩展字段即可 |
| 发布前检查（无未解决意见才放行） | `content/baselines.py::pre_publish_checks` | 闭环的关卡，已存在 |
| 「章节→小节」定位；修订记录末行解析 | `content/revision_record.py::section_labels`、`_revision_table_rows` | 改动总表、本次修订行 |
| 离线读 DOCX（zip+lxml，不依赖 Word） | `domain/ooxml.py::read_docx_package` | 会议后读回填好的纪要表文件 |

## 3. 整体流程

```
① 编辑改稿（改动面板标记出增/改/删）
        │
        ▼
② 导出会议评审稿（只含改动章节 + 附带空白评审纪要表）
        │  生成评审条目号 R01… 与条目快照（条目号↔章节↔导出时内容哈希）
        ▼
③ 会议评审（会议室无工具：打印/投屏；记录员在纪要表或纸上记录意见）
        │
        ▼
④ 意见回流（两路，落到同一处 ReviewStore）
        │  A. 导入回填好的纪要表 DOCX（离线解析，幂等去重，自动绑章节）
        │  B. 工具内直接登记（纸质/拍照口述兜底）
        ▼
⑤ 逐条处理（责任人 / 计划完成时间 / 评审记录 / 更改结果与证据 / 遗留问题）
        │
        ▼
⑥ 更改确认（confirm）→ 意见闭合
        │
        ▼
⑦ 生成正式《评审纪要》（9 列标准表，DOCX/Markdown）→ 归档/签批
        │
        ▼
⑧ 发布门禁：未解决意见 → 阻断（或签字跳过并留痕）；已解决未确认 → 提示
        │
        ▼
⑨ 发布成功 → 会话基线自动重置 → 下一轮评审从新基线开始
        ▲
        └（需复审时）再次导出评审稿，逐条目附「上轮意见及处理」，证明闭环
```

**核心思想**：会议世界与工具世界靠「评审条目号 R01… + 评审纪要编号」缝合；意见的唯一权威存储在 `.state/reviews/`，会议纪要是它的导出视图。

## 4. 功能设计

### 4.1 会议评审稿（导出）

**改动口径**：与会话基线一致（`ContentSnapshot.diff` + 重命名归并 + 改动清单），只收 `*.md` 正文、排除 `_revision_record.md`。基线只在「清除标记 / 发布成功」时重置，因此「当前基线以来的改动」天然等于「本次要评审的修订」。

**文档结构（五段式）**：

1. **信息块**：文档编号/名称、本次版本（修订记录末行）、基线时间、导出人/时间、改动统计、评审稿编号 `RS-时间戳`；
2. **本次修订记录行**：末行版本/摘要/日期/修改人原样带出，评审会顺带核对作者是否写对；
3. **改动总表**：条目号 | 章节→小节 | 改动类型 | 评审结论（留空）——快速扫全貌；
4. **逐条目正文**：修改 = 「修改前（基线）」全文 + 分隔线 +「修改后」全文（上下对照）；新增 = 标注 + 新稿；删除 = 标注 + 原文；前稿图片按当前资源尽力解析，缺失以占位标注；
5. **附录：空白评审纪要表**（9 列标准表，预填若干空行）——会议记录员可直接在此表记录，会后整表回流。

**输出与降级**：评审 Markdown → `markdown_to_word_html` → 本机 Word 转 DOCX；Word 不可用时降级交付 HTML（浏览器可开，不阻塞会议）。评审稿与条目快照 `review_items.json` 同放 `output/review/review-package-<版本>-<时间戳>/`，一次拷贝带走全部材料。

### 4.2 正式评审纪要（9 列标准表，核心交付物）

**表格结构**（两行表头，共 9 列）：

| 序号 | 提出人 | 评审问题 | 责任人 | 计划完成时间 | 更改确认 | 评审记录 | 更改结果与证据 | 遗留问题 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

> 版式对齐公司模板：第一行「责任人」跨 3 列，第二行拆分「责任人 / 计划完成时间 / 更改确认」；其余 6 列跨两行。实施前以真实模板样本校准合并单元格细节。

**数据来源**：`ReviewStore.comments` 每条意见一行，逐列回填：

| 纪要列 | 来源（ReviewComment 字段） |
| --- | --- |
| 序号 | 导出时自动 1..n（导入的原始序号保留在 `row_serial`） |
| 提出人 | `author` |
| 评审问题 | `text` |
| 责任人 | `assignee` |
| 计划完成时间 | `planned_date` |
| 更改确认 | `confirm_status`（空=未确认） |
| 评审记录 | `resolution_note` |
| 更改结果与证据 | `evidence` |
| 遗留问题 | `open_issue` |

**生成能力**：

- **空表模式**：生成 N 空行空白纪要表（供打印/会议使用，等于 4.1 的附录单独导出）；
- **闭环填充模式**：导出全部意见（可选筛选：全部 / 仅未解决 / 仅已解决 / 按责任人 / 按评审条目）；
- **信息块**：文档编号/名称、本次版本、评审纪要编号（如 `JL-文档编号-版本-时间`）、评审发起人/时间、统计（总意见/已解决/已确认/遗留）；
- **格式**：Markdown 原生必出；DOCX 经本机 Word（无 Word 降级 HTML 并提示）；
- **只读原则**：工具生成的是**新文件**，绝不改写任何用户已填写的原始纪要文件。

### 4.3 意见回流

- **导入**（主路径）：选回填后的纪要表 DOCX（本工具导出的或外来同格式均可）→ `read_docx_package` + lxml 离线解析 → 表头驱动定位（按「评审问题/提出人」等表头文本找列，容错两行表头与合并单元格）→ 一行一条意见 → 幂等键 `(评审稿编号, 原始序号)`，重复导入跳过并反馈「新增 N / 跳过 M」→ 条目号命中自动绑章节，未命中进意见面板手工绑定。
- **手工登记**（兜底）：意见对话框内直接按 9 列录入（纸质记录、拍照口述都走这里）。
- **漂移检测**：`review_items.json` 可用时比较导出时哈希，若「该条目导出后又改动了」仅提示不阻断。

### 4.4 处理与确认

状态机：**未解决**（导入/登记）→ 编辑九列字段（责任人/计划时间）→ 填评审记录/更改证据（工具可自动起草证据文本，如「章节 3.7.9 已修改，见条目 R02」）→ **已解决** → 填**更改确认** → 闭合。遗留问题可转入下一轮评审跟踪。

### 4.5 发布门禁

- 未解决意见 > 0 → **阻断**发布（既有 `pre_publish_checks`），跳过需明确签字留痕（既有 `approval_gate` 语义）；
- 已解决但更改确认为空 → 发布前检查**提示**（可跳过，二期可按项目设置收紧为硬门禁）；
- 发布成功 → 基线自动重置 → 新一轮改动口径自动刷新。

### 4.6 二轮评审与闭环证明（二期）

再次导出评审稿时，逐条目下自动附「上轮意见及处理」表（意见/责任人/评审记录/更改结果/确认状态），向评审会证明「上轮意见全部闭环」，本轮只评审新增改动。

## 6. 界面设计

- **改动面板**：标题行新增「导出评审稿」「生成评审纪要」「导入评审意见」（与「生成修订记录」并排）；
- **导出评审稿**：确认框（改动统计预览 + 基线时间 + 目标目录）→ 后台线程执行 → 完成后打开所在目录；
- **意见管理对话框**（替换现有简陋输入框）：列表（状态/已确认/责任人筛选）、双击跳转章节、按 9 列字段编辑、解决/确认、绑定章节、导入入口；
- **生成评审纪要**：选择模式（空表 / 闭环填充）、行数或筛选条件、输出目录；完成后打开。

## 8. 边界与异常

| 场景 | 处理 |
| --- | --- |
| 会议室/会场电脑无 Word | 评审稿与纪要自动降级 HTML，浏览器可看可打印 |
| 导出后内容又改 | 导入时按哈希提示「该条目自导出后又有改动」，仅提示 |
| 外来表单（非本工具导出） | 表头驱动照常解析；未绑章节手工补；幂等键回退「章节+提出人+内容哈希」 |
| 意见绑定到已删除/重命名章节 | 绑定失败置空 → 手工绑定；既有 `association_changed` 标记兜底 |
| 同一纪要重复导入 | 幂等键跳过，反馈新增/跳过计数 |
| 旧版本项目数据 | 新字段带默认值，旧 `comments.json` 直接可读 |
| 超大文档 | 评审稿只含改动章节+总表导航；二期支持勾选部分条目导出 |

## 9. 分期计划

**P0（闭环可用，一期交付）**
1. `ReviewComment` 九列字段扩展 + `update_fields`（向后兼容）
2. 导出会议评审稿（前后对照 + 空白纪要表附录 + 条目快照 + HTML 降级）
3. 导入回填纪要表（表头驱动解析 + 幂等 + 绑定 + 漂移提示）
4. 意见管理对话框（九列编辑、解决/确认、绑定章节、跳转）
5. 生成正式评审纪要（9 列表，空表/填充两模式，DOCX/Markdown）
6. 发布门禁：未解决阻断（既有）+ 已解决未确认提示
7. 自动化测试 + 使用说明

**P1**：二轮导出附「上轮意见及处理」表；勾选部分条目导出；行级对照（删红增绿）；意见↔章节树联动
**P2**：接入版本化基线支持「对比指定历史版本」；未确认收紧为硬门禁（项目设置）；纪要自动签批流程

## 10. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 纪要表合并单元格细节与真实模板有出入 | 实施前向用户索取真实纪要表 DOCX 样本，固化为解析/渲染测试夹具 |
| 基线只存正文不存前稿图片 | 前稿图片按当前资源同路径尽力解析，缺失占位标注 |
| 前后对照稿在超大文档上很厚 | 信息块+总表先行，评审人按总表挑读 |
| 会议纪要表是正式记录，不能破坏 | 工具只读导入、绝不改写原始文件；生成的一律是新文件 |
| 新字段被旧版本程序读取报错 | 单机内部工具随版本升级，接受并文档标注 |
| 外来表单绑定率低 | 手工绑定兜底 + 既有关联变更标记 |

## 11. 待确认事项

1. **真实纪要表样本**（DOCX 或 XLSX）：确认两行表头/合并单元格的精确结构，并作为解析测试夹具；
2. 纪要是否需要**签字行**（评审组长/记录人/日期）及**评审结论**区（通过/有条件通过/不通过）；
3. 纪要编号规则：`JL-文档编号-版本-时间` 是否可用，或按公司编号规则调整；
4. 「更改确认」是否要求必须填写才允许发布（P0 为提示，可收紧）。
