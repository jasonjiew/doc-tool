#### 功能描述

<!-- TBL:style=142 type=auto tw=0 cols=1242,8612 cm=0,108,0,108 ind=0:dxa lay=autofit bd=single:auto:4:0 hdr=0 va=bottom -->
| 设计编号 | Design-BREATHE-DATA-STORE-STATE-001 |
| --- | --- |
| 功能描述 | 将“原始秒级/事件数据归档”与“分钟级聚合数据归档”拆分为两条独立状态机，并补充按日 Redis 候选池、批量去重调度、MQ 异步派发和失败重投设计，保证大批量历史数据场景下的吞吐与可恢复性。 |
| 设计定位 | 在既有 15.1.1 ~ 15.1.4 主流程基础上，补充本次版本的运行态设计。重点解决历史数据积压、重复扫描、分钟级数据与原始数据归档节奏不一致、以及归档失败后无法重新派发的问题。 |
| 核心机制 | 1. 双状态字段：status 负责原始治疗/事件数据归档状态，minStatus 负责分钟级数据归档状态。 2. 按日待办池：使用 BREATHE_ARCHIVE_DATA_DAY_KEY + yyyyMMdd 记录当日待归档候选。 3. 分批+去重扫描：定时任务使用 Redis SCAN 拉取 Key，按 {deviceNo + pId} 聚合并在内存中去重，避免 N+1 查询。 4. 分布式锁保护：归档调度入口加分布式锁，防止多实例并发触发同一批归档任务。 5. 模板化归档：通过统一的 executeArchiveTask / handleArchivingData / archivingMinterData 流程，复用查询、上传、删库、状态落库逻辑。 |

#### 状态定义表

<!-- TBL:style=142 type=auto tw=0 cols=1305,942,6353 cm=0,108,0,108 ind=0:dxa lay=autofit bd=single:auto:4:0 hdr=0 va=bottom -->
| 字段 | 状态值 | 语义说明 |
| --- | --- | --- |
| status | NO | 原始秒级/事件数据未归档，热库仍保留有效数据。 |
| status | YES | 原始秒级/事件数据已完成 OSS 归档，热库已物理删除。 |
| status | UPDATE | 已归档数据发生补传或恢复写回，等待下一个归档周期重新归档。 |
| status | FAIL | 原始数据归档执行异常，需保留待办信息并等待后续补偿。 |
| minStatus | NO | 分钟级聚合数据未归档。 |
| minStatus | YES | 分钟级聚合数据已完成 OSS 归档，Mongo 分钟表已删除源数据。 |
| minStatus | FAIL | 分钟级聚合数据归档失败，需要重新扫描并重试。 |

#### 接口设计

<!-- TBL:style=142 type=auto tw=0 cols=3603,3321,2930 cm=0,108,0,108 ind=0:dxa lay=autofit bd=single:auto:4:0 hdr=0 va=bottom -->
| 核心方法 | 入参设计 | 职责与设计意图 |
| --- | --- | --- |
| timingColdDataArchivingByDay | LocalDate targetDate / void | 归档调度入口。按日扫描 Redis 候选池，并基于内存分组结果驱动原始数据和分钟级数据归档。 |
| processBatch | List<String> batchKeys, Set<String> processedUserSet | 批处理器。负责分组、跨批次去重和批量删除 Redis Key，是避免 N+1 查询的核心。 |
| handleArchivingData | ArchivedMetadata metadata | 原始秒级治疗数据与事件数据归档执行器，负责查询、上传、写元数据、删热库。 |
| archivingMinterData | ArchivedMetadata metadata | 分钟级数据归档执行器，独立维护 minStatus。 |
| handleArchivedDataAndRestore | BreatheAggregationDto aggQuery | 查询链路前置哨兵。当业务查询的日期已归档时，自动恢复 OSS 冷数据并将状态切为 UPDATE。 |
| restoreOssTreatmentData | ArchivedMetadata metadata | 归档恢复执行器。负责从 OSS 下载 JSON/JSON.GZ、流式解析并回写 MongoDB。 |

#### 核心逻辑

<!-- TBL:style=142 type=auto tw=0 cols=1356,5229,3269 cm=0,108,0,108 ind=0:dxa lay=autofit bd=single:auto:4:0 hdr=0 va=bottom -->
| 执行步骤 | 详细逻辑说明 (Step-by-Step) | 业务约束与红线 |
| --- | --- | --- |
| 第一步：按日登记候选 | 每当结果集落库、分钟级聚合完成、或历史补传导致数据发生变化时，将 {deviceNo, cureDate, pId} 写入按日 Redis SET 待办池。 | 红线：候选登记属于旁路能力，禁止因 Redis 写入失败阻断主业务保存。 |
| 第二步：获取调度锁 | 任务启动前先抢占分布式锁，只有持锁实例可以继续执行后续扫描与派发。 | 红线：未持锁实例必须立即退出，禁止多实例同时操作同一批次候选集合。 |
| 第三步：SCAN 分批读取 | 调度任务每次按批次从 Redis 扫描待办 Key，单批仅在内存中保留有限数量的坐标集合。 | 性能约束：禁止 SMEMBERS 全量拉取全部待办，避免大 Key 导致 OOM。 |
| 第四步：设备维度去重 | 使用 {deviceNo + pId} 作为聚合键，对同一设备在一个调度周期内只做一次“积压天数”检查。 | 红线：未去重前禁止逐条访问 Mongo 统计未归档天数，否则会形成明显 N+1。 |
| 第五步：分离状态推进 | 原始数据链路只更新 status；分钟级链路只更新 minStatus。两者互不覆盖，允许出现“原始已归档、分钟未归档”或相反状态。 | 设计意图：分钟表和秒级表数据量、修复频率、回算节奏不同，必须解耦。 |
| 第六步：模板化归档执行 | 统一走“构建查询参数 -> 查询数据 -> 生成 OSS 路径 -> 上传 -> 更新元数据 -> 删除热库 -> 保存状态”的模板方法。 | 红线：任何删库动作必须发生在 OSS 上传成功且元数据写入成功之后。 |
| 第七步：失败重投与顺延 | 若本批次归档失败，将失败 Key 保留或迁移到下一日待办集合，等待后续定时任务重新派发。 | 约束：失败记录不得被提前移出候选池，否则会导致永久漏归档。 |
