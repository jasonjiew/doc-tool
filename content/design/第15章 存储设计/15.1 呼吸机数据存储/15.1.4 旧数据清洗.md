#### 功能描述

<!-- TBL:style=142 type=auto tw=0 cols=1242,8612 cm=0,108,0,108 ind=0:dxa lay=autofit bd=single:auto:4:0 hdr=0 va=bottom -->

| 功能描述 | 对系统上线至优化前的历史秒级数据进行批量清洗和归档，将无效或异常数据剔除，按分钟级聚合规则生成标准分钟级数据，同时归档原始秒级数据至 OSS，保证数据完整性、准确性及追溯能力。 |
| 设计定位 | 高性能增量清洗工具。利用 Redis 维护一份“元信息变动时间表”，记录每个设备数据的最后更新时刻，以此作为增量清洗的“水位线”，确保历史数据清洗的高效与不重不漏 |
| 核心机制 | 1. Redis 变动追踪：每当数据变动时，在 Redis 中更新该设备的时间戳。 2. 指标对齐清洗：对比 Redis 中的变动记录与分钟表的最后记录时间。 3. 逻辑引擎复用：强制调用标准降维算法（15.1.3 章节），保证数据一致性。 |

#### 核心逻辑

<!-- TBL:style=142 type=auto tw=0 cols=1016,5491,3347 cm=0,108,0,108 ind=0:dxa lay=autofit bd=single:auto:4:0 hdr=0 va=bottom -->
| 执行步骤 | 详细逻辑操作说明 (Step-by-Step) | 业务约束与红线 |
| --- | --- | --- |
| 第一步：变动信息维护 | 前置逻辑：在任何数据补传、修改秒级数据的接口中，同步执行 HSET 操作。Key 为 CLEAN_META:deviceNo，Field 为 date，Value 为当前系统时间戳（update_time）。 | 设计意图：利用 Redis 维护一份轻量级的“数据变动索引”，避免为了找增量数据而去扫描 MongoDB 的几亿行记录。 |
| 第二步：扫描变动名单 | 清洗任务启动后，首先通过 Redis 的 HGETALL 或 HSCAN 提取所有存在 update_time 记录的设备与日期坐标。 | 红线：禁止全量扫描 MongoDB。必须以 Redis 中的变动标识作为“任务源”，实现精确打击。 |
| 第三步：增量水位判定 | 将 Redis 中的 update_time 与该设备在分钟聚合表中的 last_agg_time（上次执行时间）进行对比。若 update_time >  last_agg_time，则触发清洗。 | 逻辑约束：如果两次时间一致，说明该天数据自上次聚合后未发生任何变化，直接跳过，节省计算资源。 |
| 第四步：执行标准化降维 | 满足判定条件的记录，逐一进入降维引擎。执行：拉取秒级数据 -> 窗口分桶 -> 极值计算 -> 批量 Upsert 入库。 | 复用红线：必须复用 15.1.3 的代码。严禁在此处编写独立的 SQL/逻辑，防止清洗出的历史数据与实时数据标准不一。 |
| 第五步：更新清洗进度 | 聚合入库完成后，同步更新 Redis 中对应的 last_agg_time 标识，完成当前坐标的“增量闭环”。 | 约束：若任务失败，严禁更新进度位。保留 Redis 中的旧时间戳，以便下次任务重新扫描处理。 |
| 第六步：限流与平滑处理 | 针对存量超大数据的首次清洗，采用分页拉取 Redis Key 并在批次间加入 sleep(200ms)。 | 性能红线：手动清洗不能影响生产环境的响应速度。必须控制 MongoDB 的连接数与写入吞吐量。 |
