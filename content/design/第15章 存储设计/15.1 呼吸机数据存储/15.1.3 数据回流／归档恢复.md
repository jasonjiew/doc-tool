#### 功能描述

<!-- TBL:style=142 type=auto tw=0 cols=2235,7619 cm=0,108,0,108 ind=0:dxa lay=autofit bd=single:auto:4:0 hdr=0 va=bottom -->
| 设计编号 | Design-BREATHE-DATA-STORE-A**RT-S-001** |
| --- | --- |
| 功能编号 | REQ-DATA-STORE-007/008/009 |
| 用户需求编号 | / |
| 功能描述 | 本功能负责将已转储至 OSS 冷库的历史明细数据重新恢复至 MongoDB 热库。 |
| 设计定位 | 实现“冷数据无感回温”。解决因数据归档导致的历史波形无法查询或历史数据补传无法入库的问题。确保业务层在调用数据时，无需感知数据是存储在热库还是冷库。 |
| 核心机制 | 1. 状态感知触发：系统监测到数据上传或查询请求时，实时核对 sys_archived_metadata 表。若状态为 YES（已归档），则自动触发恢复流程。 2. 动态拉取解压：调用 restoreOssTreatmentData 接口，从 OSS 唯一定位压缩文件，下载并在内存中执行 GZIP 解压。 3. 脏数据标记：恢复后的数据在元数据表中标记为 UPDATE，以便后续归档调度器再次对其进行静默处理。 |
| 触发条件 | 每当消费实时治疗数据 |

#### 15.1.3.5 核心逻辑

<!-- TBL:style=142 type=auto tw=0 cols=937,5207,3710 cm=0,108,0,108 ind=0:dxa lay=autofit bd=single:auto:4:0 hdr=0 va=bottom -->
| 执行步骤 | 详细逻辑操作说明 (Step-by-Step) | 业务约束与红线 |
| --- | --- | --- |
| 第一步：前置状态扫描 | 每当有数据上传请求进入时，系统首先以 {deviceNo, cureTime, pId} 为组合索引，在 sys_archived_metadata 表中检索是否存在 status = 'YES' 的记录。 | 红线：禁止先写数据再查状态。必须先判定归档状态，否则会导致补传的数据与冷库数据在逻辑上产生断层。 |
| 第二步：冷库数据定位 | 若命中已归档状态，逻辑层立即从元数据中提取 filePath（OSS 路径）和 fileName。 | 约束：若元数据记录存在但 OSS 文件丢失，必须抛出异常并记录审计日志，严禁静默失败。 |
| 第三步：内存流式解压 | 调用 OSS SDK 获取 InputStream，随后嵌套 GZIPInputStream。程序通过缓冲区（Buffer）分批读取解压后的 JSON 字节流，并利用 Jackson 框架反序列化为对象列表。 | 红线：严禁使用 IOUtils.read() 一次性加载整个文件到内存，必须采用流式解析以防止 OOM。 |
| 第四步：热库幂等回填 | 将解压出的历史数据与本次补传的新数据在内存中合并，然后调用 MongoDB 的 bulkWrite。 | 约束：必须使用 upsert: true 模式。根据时间戳索引进行覆盖写入，确保历史冷数据和补传新数据完美融合，无重复记录。 |
| 第五步：状态机翻转 | 数据库操作完成后，将该条元数据的 status 字段从 YES 修改为 UPDATE，并清除旧的 filePath（可选）。 | 设计意图：设为 UPDATE 是为了告知“归档调度器”：该日数据已发生变动，请在下一个归档周期重新扫描并再次下沉至冷库。 |
