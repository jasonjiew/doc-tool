#### 功能描述

| 用户需求编号 | / |
| 功能描述 | 本功能旨在解决呼吸机设备高频上报导致的热点数据库（MongoDB）存储成本骤增与性能衰退问题。 |
| 设计定位 | 实现一套 “推模式触发 + 异步削峰”的冷热数据分离机制。将满足衰退周期（如 >31天）的历史明细数据，从昂贵的高性能热库，降级转储至低成本的对象存储（OSS），并从热库中彻底物理抹除 |
| 核心机制 | 1. 惰性登记：不在全局进行昂贵的全表过期扫描。而是在业务端产生每日统计指标时，顺手将涉及的设备坐标登记到当天的“待归档候选池”中。 2. 按需派发：调度中心定时巡检候选池，仅当设备的未归档数据积压天数达到阈值时，才生成归档任务投递至消息队列。 3. 流式瘦身：消费端接管重负载任务，将热库数据抽取后进行流式 GZIP 压缩并归档至 OSS，最终完成热库的物理瘦身。 |
| 触发条件 | 当结果集数据有修改时 |

#### 15.1.2.5 核心逻辑

<!-- TBL:style=142 type=auto tw=0 cols=1668,4826,3360 cm=0,108,0,108 ind=0:dxa lay=autofit bd=single:auto:4:0 hdr=0 va=bottom -->
| 执行步骤 | 详细逻辑操作说明 (Step-by-Step) | 业务约束与红线 |
| --- | --- | --- |
| 第一步：坐标异步登记 | 在每日指标计算（统计任务）落库完成后，同步提取 {deviceNo, cureTime, pId} 关键信息。调用 timerArchivedCache 将此坐标以字符串形式推入 Redis 的 SET 集合中（Key 按天对齐）。 | 红线：此步骤必须被 try-catch 包裹，作为旁路逻辑执行。绝对禁止因为写入 Redis 失败而导致主业务（统计任务）回滚。 |
| 第二步：调度扫描与聚合 | 凌晨定时任务启动，使用 SCAN 命令分批从 Redis 中提取坐标名单。在内存中按照 {deviceNo + pId} 进行 Group By 聚合，过滤掉同一个人在同一天内的重复记录。 | 约束：必须在内存中完成初次去重。严禁直接拿着 Redis 的原始名单逐条去扫数据库，防止产生 N+1 查询压力。 |
| 第三步：归档阈值判定 | 拿着去重后的名单，去 MongoDB 查询该设备处于“未归档”状态（status='NO' 或 'UPDATE'）的总天数。计算公式为：today -  earliest_unarchived_date。 | 红线：只有当积压天数 > 31天 时，才判定为“满足归档条件”。如果不满 31 天，则直接跳过，保留在热库。 |
| 第四步：任务派发与分发 | 对满足条件的设备，组装 MQ 消息（包含设备号、归属患者、日期范围）。消息投递至 RabbitMQ 归档专用队列，实现调度与执行的解耦。 | 设计意图：通过 MQ 削峰填谷，防止凌晨大批量归档任务集中爆发，导致服务器 IO 或带宽瞬间过载。 |
| 第五步：执行流式压缩上传 | 消费端收到消息后： 1. 从 MongoDB 查出目标日期所有秒级/分钟级明细。 2. 开启 GZIPOutputStream 流。 3. 边遍历数据集，边将其序列化并推入压缩流。 4. 将生成的 .json.gz 文件直连上传至 OSS。 | 红线：禁止一次性 fetch 全量数据到内存。必须使用 MongoCursor 游标逐条读取数据并写入压缩流，防止触发 OOM。 |
| 第六步：元数据更新与销毁 | 1. 记录归档元数据 sys_archived_metadata，保存 OSS 路径、文件大小、时间切片信息。 2. 确认元数据落库后，执行 MongoDB 物理删除动作，释放磁盘空间。 | 物理删除红线：删除动作必须放在 OSS 上传成功且元数据落库成功之后。若前置步骤失败，严禁执行删除，确保数据不丢失。 |
| 第七步：消息签收闭环 | 所有的 DB 操作和 OSS 操作完成后，执行 channel.basicAck 确认消息完成。 | 约束：若执行中途发生异常，执行 basicNack 且 requeue=false，将错误指令转入死信队列人工核查。 |
