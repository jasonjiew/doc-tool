#### 核心逻辑

##### 患者新增/编辑

<!-- TBL:style=45 type=pct tw=5000 trh=5211 cols=1252,8602 cm=0,108,0,108 ind=0:dxa lay=fixed bd=single:auto:4:0 va=center -->
| 功能 | 核心逻辑描述 |
| --- | --- |
| 新增 | 设备代码提取：首先从输入参数patientInfoIn中提取deviceCode。 身份证验证： 如果patientInfoIn中的身份证号码不为空， 使用baseMapper查询数据库中是否存在相同身份证号码的记录。 如果查询结果不为空（即身份证号码已存在），则抛出运行时异常，错误信息为“系统中身份证号码已存在”。 基本信息添加： 创建一个Info对象，并将patientInfoIn的属性复制到Info对象中。 为Info对象生成一个序列号作为code，并设置channelSource为特定的字符串。 获取当前登录用户的信息，通过用户名查询员工信息。 如果查询结果不为空，则将查询结果的第一个元素的empId赋给Info对象的doctorId。 将Info对象保存至数据库。 患者与机构关联： 创建一个PatientInstitutionInfo对象，设置其institutionId为当前登录用户的部门ID，patientId为刚刚保存的Info对象的ID，createDate为当前时间。 将PatientInstitutionInfo对象保存至数据库。 设备绑定： 如果deviceCode不为空， 创建一个DeviceInfoAppIn对象，设置其userId为Info对象的ID，deviceCode为patientInfoIn中的deviceCode。 调用远程服务remoteBreatheDeviceService的managerBindDevice方法进行设备绑定。 如果设备绑定失败（即返回结果的状态码不是成功状态），则抛出运行时异常，错误信息为设备绑定失败的具体信息。 返回结果：如果上述所有操作都成功，返回一个表示成功的响应结果。 |
| 编辑 | 1.根据传入的patientInfoIn对象中的id，更新患者的基本信息，包括姓名、身份证号、体重、身高、地址、病历号、诊断结果、医生姓名和预充血容量。 2. 根据传入的patientInfoIn对象中的deviceCode和preDeviceCode进行设备解绑和绑定的逻辑判断与处理。 - 如果当前设备号为空，则直接返回成功结果，无需进行设备操作。 - 如果之前的设备号为空，则直接调用远程设备服务进行设备绑定操作，并判断操作是否成功，如果失败则抛出异常。 - 如果当前设备号和之前的设备号不一致，则先调用远程设备服务进行设备解绑操作，再进行设备绑定操作，并判断操作是否成功，如果失败则抛出异常。 |

##### 每日详情

<!-- TBL:style=45 type=pct tw=5000 trh=3061 cols=2047,7807 cm=0,108,0,108 ind=0:dxa lay=fixed bd=single:auto:4:0 va=center -->
| 功能 | 核心逻辑描述 |
| --- | --- |
| 获取设备使用日期列表 | 用于查询指定设备在一段时间内的实际使用日期，返回去重、排序后的日期列表，支持前端展示“用户哪天使用过设备”的基础数据。 步骤1：时间范围校准（核心业务规则） - 若传入 `queryDate`，默认查询 `queryDate前30天` 至 `queryDate当天`** 的时间范围； - 若未传入 `queryDate`，默认查询 `当前日期前30天` 至 `当前日期`** 的时间范围； - 若计算的起始时间早于设备首次使用时间，自动调整为设备首次使用时间（避免查询无效历史）； - 时间范围最大跨度严格限制为30天（防止超大数据量查询，优化性能）。 步骤2：数据查询（多数据源适配） 通过 `BreatheResultRepository` 执行查询，核心SQL逻辑 - 依赖 `breathe_result` 表（每日治疗结果汇总表），该表记录了每次治疗的结束时间、时长等； - 若数据已归档（通过 `BreatheArchivedRepository` 判断），则查询归档表 `breathe_result_archived` 步骤3：数据查询（多数据源适配） - 去重：通过 `DISTINCT` 确保每个日期仅出现一次； - 排序：按日期倒序排列（最新使用日期在前）； -封装VO：为每个日期生成自增 `id`（前端渲染时用于索引），最终返回 `List<BreatheUsageDaysVo>` |
| 生成每日呼吸详情报告 | 核心业务方法，根据设备编码和指定日期，生成包含压力、事件、泄漏、潮气量等关键指标的详细报告，支撑前端展示 “某日的完整呼吸数据波形与统计值”。 步骤 1：参数校验（前置防御） 校验 deviceCode、queryDate、patientId 非空，若为空则抛出 IllegalArgumentException（错误信息：“设备编码 / 查询日期 / 患者 ID 不能为空”）； 校验 queryDate 合理性（不能晚于当前日期，避免查询未来数据）。 步骤 2：时间范围与患者 ID 处理（精准定位数据） 调用辅助方法 handleTimeRangeAndPatientId，输出以下关键参数： 实际查询时间范围： 基准范围：queryDate 00:00:00 至 queryDate 23:59:59； 校准后范围：结合首条 / 末条治疗记录时间，扩展为 startTime（首条记录时间的整点）至 endTime（末条记录时间 + 1 小时后的整点）； 补偿时间： compensationStart：startTime 与首条治疗记录时间的分钟差（用于填充前序缺失数据）； compensationEnd：endTime 与末条治疗记录时间的分钟差（用于填充后序缺失数据）； 步骤 3：查询设备设置（区分治疗模式） 通过 RemoteBreatheDeviceService.getDeviceSetting(deviceCode) 获取设备配置，核心信息： treatmentMode：治疗模式（TreatmentModeEnum.SINGLE 单水平 / DOUBLE 双水平）； pressureRange：压力范围（如单水平 8-12cmH₂O，双水平 IPAP 10-15、EPAP 5-8）； 模式决定后续指标计算逻辑（如双水平需单独处理吸气 / 呼气压力，单水平仅处理总压力）。 步骤 4：查询分钟级聚合数据（核心数据源） 调用 queryMinuteAggregateData 从 breathe_cure 表（实时治疗表）或归档表查询数据，返回 List<MinuteAggregateBo>，每条记录包含： 时间戳（minuteTime，精确到分钟，如 2025-09-01 02:30:00）； 压力指标（ipap 吸气压力、epap 呼气压力、pressure 总压力）； 泄漏指标（leakage 泄漏值）； 潮气量（tidalVolume，仅双水平）； 呼吸频率（respiratoryRate，仅双水平）等。 步骤 5：处理分钟数据（指标计算与波形生成） 调用 processMinuteData 处理 List<MinuteAggregateBo>，核心逻辑： 指标有效值计算：通过 BreathRepCalcUtils.calcValidValue() 对每个指标取有效值（如压力取分钟内平均值，泄漏取 95% 分位值）； 模式差异化处理： 单水平：仅保留 pressure 字段，计算其平均值、P95 值（95% 时间内的压力值）； 双水平：分别计算 ipap、epap、tidalVolume 等指标的统计值； 波形数据生成：将每分钟的有效值按时间顺序存入列表（如 pressureWaveform: [8.2, 8.5, ..., 9.1]），用于前端绘制波形图。 步骤 6：填充缺失时间（保证数据连续性） 调用 fillMissingTimes 补全时间序列： 若原始数据存在时间断点（如 2:30 至 2:35 无数据），在对应位置填充 null； 结合 compensationStart 和 compensationEnd，在数据前后补充缺失的分钟点（如治疗从 02:15 开始，需在 00:00-02:14 填充 null）； 最终确保时间序列覆盖 startTime 至 endTime 的每一分钟（总长度 = (endTime - startTime) / 60 分钟）。 |
